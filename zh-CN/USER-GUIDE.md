# 虚拟硬盘系统 —— 使用说明

## 这是什么

一个**不用 U 盘、不用进 BIOS、不用 PE** 的装系统工具。

双击运行后，它会把你指定的系统镜像装成一个**独立的虚拟硬盘系统**。
重启电脑，开机菜单会多出一项（就是你给这个系统起的名字），选它就进新系统；选原来那项就回老系统。

**原系统完全不会被改动。** 新系统本质上就是某个文件夹里的一个 `.vhdx` 文件，
不想要了运行卸载工具就能彻底删掉，像删掉一个大文件一样干净。

### 能装多个，名字和位置都自己定（v1.11 起）

以前只能装一个，而且 vhdx 文件名写死成 `NewSystemDisk.vhdx`，目标文件一存在就直接报错。
现在：

- **自己起名字**：第 ③ 步填一个名字（中文、英文都行）。这个名字就是开机菜单里显示的那一行，
  也是 vhdx 文件的文件名。比如填「游戏系统」，就生成 `游戏系统.vhdx`，菜单里显示「游戏系统」。
- **想装几个装几个**：装完一个，关掉窗口重新打开，换个名字再装一次即可。
  每个系统是独立的 vhdx，互不影响，菜单里各占一项。
- **存放位置自由选**：第 ② 步既可以点硬盘按钮一键填盘符，也可以手输/浏览任意文件夹
  （如 `D:\VHD`、`E:\系统\游戏`）。程序会自动建子目录吗？不会 —— 目录得先存在，
  或者用「浏览」新建。
- **重名自动加序号**：同一个文件夹里已经有 `游戏.vhdx` 了，再装同名会自动变成 `游戏(2).vhdx`
  （菜单名字仍然是「游戏」，如果你想要菜单名也不一样，直接改名字就好）。

名字的合法范围：非法字符 `\ / : * ? " < > |` 会被自动去掉，emoji 不支持（会明确提示），
最长 48 个字符。`CON`、`PRN` 这类保留名会自动变成 `CON-`。

存放位置的限制（都会在界面上直接提示，不会装到一半才失败）：

| 要求 | 原因 |
|---|---|
| 必须是 **NTFS** 分区 | exFAT/FAT32 不支持 vhdx 需要的稀疏文件 |
| 必须是 **本地固定硬盘** | U 盘 / 移动硬盘 / 网络盘在开机那一刻可能根本没挂上，系统起不来 |
| 不能放进 `Windows` / `Program Files` / `Program Files (x86)` / `ProgramData` / `Users` | 权限受限，而且容易被系统清理工具盯上 |
| 剩余空间 ≥ 设定大小 + 5GB | 留余量防写满 |

### 支持哪些镜像格式？

三种都行，直接选那个文件就好：

| 格式 | 说明 | 举例 |
|---|---|---|
| `.wim` | 最常见。Dism++ 导出的、原版光盘里 `sources\install.wim` | `maimai3.wim`、`install.wim` |
| `.esd` | 微软官方 ISO 里常见的压缩版（体积更小），DISM 原生支持 | `install.esd` |
| `.iso` | **整个 Windows 安装光盘镜像**，程序会自动挂载并取出里面的系统 | `Win10_22H2.iso` |

选 `.iso` 时程序会在后台自动挂载它（多出一个光驱盘符），装完自动卸载，
不需要你手动去「装载」。

> 官方镜像的索引 1 有时是「Windows PE」或「Windows Setup」而不是真正的系统，
> 程序会自动跳过这一类，选真正能装的那个索引。


### 虚拟磁盘能正常用吗？

能。它对你来说就是一块普通的硬盘：

- 能存文件、装软件、装驱动、跑 Windows Update
- 系统盘多大，你设的那个 GB 数就是多大（比如设 100GB 就是一个 100GB 的 C 盘）
- **动态扩容**：初始只占几十 MB，用多少长多少，不会立刻吃掉 100GB

唯一区别是它的"盘体"就是那个 `.vhdx` 文件。所以：

- 这个 vhdx 文件在你**当前系统里删不掉**（正在被新系统使用），要删得先进老系统
- 想搬到别的电脑，把 vhdx 拷过去再重建启动项就行
- 性能比物理磁盘略低（多一层文件系统），日常办公、装软件完全感觉不到

```
│   ├─ 新系统-诊断并装驱动.bat
│   ├─ 新系统-清理幽灵显卡.bat
│   ├─ 全量注入驱动-管理员运行.bat
│   ├─ 注入网卡驱动-管理员运行.bat
│   ├─ 修好菜单指向-管理员运行.bat
│   ├─ 修复启动菜单-管理员运行.bat
│   ├─ 清理安装残留-管理员运行.bat
│   ├─ 清理ESP盘符-管理员运行.bat

└─ _源码\                     ← 11 个 ps1 和打包脚本，可以删
```

**大多数时候你只用 `开始.bat`。** 它会列出全部功能，输入序号回车就执行；
每个工具跑完会回到菜单，不用重新双击文件。

| 功能 | 入口 | 什么时候用 |
|---|---|---|
| 装系统 | `双击我-装系统.bat` | 装独立的虚拟系统，**可装多个**，名字和存放位置自己定，原系统不动 |
| 卸载新系统 | `双击我-卸载新系统.bat` | 按名字删掉某个虚拟系统，其他的不受影响 |
| 诊断并装驱动 | `急救工具\新系统-诊断并装驱动.bat` | **在虚拟系统里跑**。还有设备带感叹号，按硬件 ID 补驱动 |
| 显卡体检 | `急救工具\新系统-清理幽灵显卡.bat` | **在虚拟系统里跑**。任务管理器多一张空 GPU（真凶是虚拟显示器），或想清掉幽灵记录 |
| 全量注入驱动 | `急救工具\全量注入驱动-管理员运行.bat` | 设备管理器一堆未知设备，整批搬 160+ 个驱动包（自动排除虚拟显示驱动，避免新系统多出空 GPU） |
| 注入网卡驱动 | `急救工具\注入网卡驱动-管理员运行.bat` | 只是没网，只搬网络类驱动（含系统内置网卡包，v1.2 起） |
| 修好菜单指向 | `急救工具\修好菜单指向-管理员运行.bat` | 菜单里有这一项，但一选就报错 / 找不到文件。核对并改正菜单指向的 vhdx 路径 |
| 修复启动菜单 | `急救工具\修复启动菜单-管理员运行.bat` | 重启没有菜单项，补注册，不用重装。**任意名字、任意目录都能找到**（v1.4 起） |
| 清理安装残留 | `急救工具\清理安装残留-管理员运行.bat` | 装到一半卡住 / 提前关窗口，清 dism 进程、挂着的虚拟盘、本工具留下的半成品 vhdx（自定义名字也认，别人的 vhdx 默认不碰） |
| 清理残留盘符 | `急救工具\清理ESP盘符-管理员运行.bat` | 多出一个 `S:` 之类的盘符 |
| 还原开机菜单 | `急救工具\还原启动菜单-管理员运行.bat` | 卸载后开机菜单还弹出来 |

**发给别人时把整个「虚拟硬盘系统」文件夹一起打包**（`开始.bat` 靠相对路径调用
`急救工具\` 里的工具，只拷根目录那几个文件，菜单会提示"找不到"）。
系统镜像（`.wim` / `.esd` / `.iso`）要另外单独提供（20GB 级别，一般另存硬盘或用网盘传）。

> **全量注入驱动请先掂量一下。** 它会把本机 160+ 个驱动包（含显卡）一次性灌进虚拟磁盘，
> 好处是设备管理器干净，代价是首次进新系统 PnP 枚举会明显变慢（真机上见过好几分钟），
> 个别不兼容的驱动还可能让新系统直接蓝屏 —— 蓝屏了连安全模式都不好进（它是个 vhdx）。
>
> 稳妥的顺序是：**先「注入网卡驱动」**（只搬网络类包，有网就能自己下驱动）→
> 进新系统确认能上网、能正常关机 → 再回来补「全量注入驱动」。
> 反正虚拟磁盘随时能重装，20 分钟的事，别一上来就梭哈。

## 怎么用

### 第一步：准备好系统镜像

需要一个 `.wim`、`.esd` 或 `.iso` 文件，三种都支持。程序会自动在以下位置搜索：

- 本程序的所在目录（含往下两层子文件夹）
- 上一级目录
- `下载`、`桌面`
- 所有本地磁盘的根目录

如果没自动找到，点「浏览...」手动选，或者直接把镜像文件拖进窗口。

> 放 `.iso` 也行 —— 不用自己解压，程序会挂载后自动找里面的 `sources\install.wim`
> 或 `sources\install.esd`。第三方精简版 ISO 如果目录结构不一样，程序也会递归找一遍。

### 第二步：选择存放位置

界面上是一个**可编辑的路径框**，下面一行是这台机器上能用的硬盘按钮（点一下就把路径填成该盘根目录），
右边还有「浏览...」可以选任意文件夹。

路径的硬性要求（不符合会立刻在下面那行红字里说明原因）：

- 必须是 **NTFS** 格式
- 必须是**本地固定硬盘**（U 盘、移动硬盘、网络盘、光驱都不行）
- 不能是 `Windows` / `Program Files` / `ProgramData` / `Users` 这些系统目录
- 剩余空间要 ≥ 设定大小 + 5GB

v1.11 之前的版本只能从下拉框挑一个盘符、vhdx 只能落在盘根；
现在可以填 `D:\VHD`、`E:\系统\游戏` 之类的子目录（目录要先存在）。

**不会格式化分区，不会动已有文件。** 新系统就是该目录下的一个 `.vhdx` 文件。

磁盘大小默认会按镜像解压后体积自动算（一般是解压体积 × 1.3），也可以手动调。
这个是**上限**，不是实际占用 —— VHDX 是动态增长的，用多少长多少。

### 第三步：给系统起名字

填一个名字，它会同时用于两处：

1. **vhdx 文件名** —— `名字.vhdx`
2. **开机菜单里的显示文字** —— 重启后选的就是这一行

输入框旁边有两个小按钮：

- **用版本名**：自动填镜像里的版本名（如「Windows 10 专业版」），省得自己打
- **加序号**：在名字后面加 `(2)`、`(3)`，方便同一个镜像装多个系统

名字下方那行会实时显示「最终会生成什么文件、在哪个目录、是否重名自动加序号」。

非法字符（`\ / : * ? " < > |`）会自动去掉；emoji 不支持，会提示你换一个；
最长 48 字符；`CON`、`PRN` 这类保留名会自动变成 `CON-`。

下面的「这台机器上已经装过的系统」会列出当前所有已装的虚拟系统，避免起重复的名字。

### 第四步：点「开始安装」

会弹一次确认（列出系统名称 / 镜像 / 位置 / 大小），确认后开始。整个过程：

| 阶段 | 大概耗时 | 说明 |
|---|---|---|
| 创建虚拟磁盘 | 几秒 | |
| 分区格式化 | 几秒 | |
| **恢复系统文件** | **10～40 分钟** | 最慢的一步，界面有实时百分比 |
| 配置启动菜单 | 几秒 | |

期间**不要关机、不要休眠**。可以干别的事，但别让电脑睡眠。

装完会问你要不要现在重启。

### 第五步：重启，选新系统

重启后会出现启动菜单（Windows 启动管理器）。

- 选**你起的那个名字** → 进新系统
- 选另一项（或者超时不管它）→ 进原来的系统

菜单默认停 10 秒，什么都不按就自动进原系统。开机时连按几下**方向键**就能提前停住。

第一次进新系统，Windows 会做几分钟初始化（转圈、准备设备之类），属于正常现象。

> **如果重启后压根没看到菜单，直接进了原系统**：
> 运行 `急救工具\修复启动菜单-管理员运行.bat`，30 秒补好启动项，**不用重新安装**。
> 详见下面「v1.4 修复」一节。
>
> **如果菜单里看到了名字，一选却报错（0xc000000f / 找不到文件）**：
> 运行 `急救工具\修好菜单指向-管理员运行.bat`，它会把菜单里指错的路径改回来。
> v1.13 之前的版本装到子目录（如 `D:\虚拟磁盘\`）会踩这个坑。

## 装完之后

### 新系统里能用什么

新系统是一份完整的 Windows 10 专业版。你的硬件驱动 Windows 会自己装大部分，
但有几件事要知道：

**1. 新系统看不到原系统的文件**
它是独立的，原 C 盘在它看来是另一个盘。想拷数据，进新系统后去「此电脑」找原来的 C 盘（盘符可能变了）。

**2. 不要在新系统里格式化任何你不认识的盘**
特别是那个放着你起的名字的 `.vhdx` 文件的分区，那是新系统自己的**外衣**，删了就没了。

**3. 如果新系统进不去（蓝屏 0x7B / INACCESSIBLE_BOOT_DEVICE）**
说明镜像里的存储驱动和这台机器不匹配。这种情况：
- 开机选原系统进老系统（老系统肯定还能进）
- 运行卸载工具删掉新系统
- 这个镜像不适合这台机器

> 补充：本工具在 UEFI 下写引导时用了 `/f UEFI`，正常情况下 Windows 10 自带的
> storahci / stornvme / iaStorAVC 驱动能覆盖绝大多数机器。如果目标机器是 RAID 模式
> （Intel RST）或特殊存储控制器，需要在 BIOS 里把 SATA 模式改成 AHCI，或者提前给镜像注入驱动。

### 卸载新系统

运行 `双击我-卸载新系统.bat`（**必须在原系统里跑**）：

1. 它会自动扫出所有装过的虚拟系统（各固定 NTFS 盘的根目录和下一层子目录里的 `*.vhdx`），
   列表里每条显示**系统名称 + 占用空间 + 文件路径**
2. 选中要删的那个，点「删除选中的系统」
3. 会删掉虚拟硬盘文件 + 移除开机菜单里对应的那一项

装过多个系统的，这里就是多条，**删一条只影响那一个**，其他的不受影响。

原系统不受影响。删完开机菜单就恢复原样了。

菜单是分三层清的：

- **按记录删**：安装时会在 vhdx 旁边写一个 `名字.boot.txt`，里面记着启动项 GUID、安装前的 `timeout` 和 `displaybootmenu`。卸载时先按这个 GUID 精确删。
- **兜底扫库**：状态文件丢了也不怕，会扫 `bcdedit /enum osloader /v`，先按**完整设备路径**（`vhd=[D:]\目录\名字.vhdx`）精确匹配；对不上再退回「同盘符 + 同文件名」；最后才放开成只看文件名（这时会明确警告可能命中别的盘上的同名系统）。
- **还原菜单开关**：删掉条目后把 `timeout` 和 `displaybootmenu` 还原成安装前的值。安装前压根没设过 `displaybootmenu` 的，用 `bcdedit /deletevalue` 恢复成「未设置」——单系统机器照样直接进系统，多系统机器原来的菜单也不会被关掉。

如果仍然残留，用 `急救工具\还原启动菜单-管理员运行.bat` 手动关一次。

> v1.6 起加了一道闸：**在新系统里运行卸载工具会被拒绝**（检测系统盘是否在 `File Backed Virtual` 磁盘上）。
> 因为在新系统里删只会改到自己那份引导，开机菜单里的条目还在，反而让人以为卸载失败了。

## 关于 ISO / ESD 格式的补充说明

### ISO 是怎么处理的

选 `.iso` 之后，程序在安装开始时会：

1. 用系统自带的 `Mount-DiskImage` 把 ISO 挂载成一个光驱盘符
2. 在里面依次找 `\sources\install.wim` → `\sources\install.esd`
   （都找不到就递归搜 `install.*`，兼容第三方精简版）
3. 拿找到的这个文件去装
4. **无论成功还是失败，最后都会自动卸载 ISO**，不会留下多余的光驱盘符

所以 ISO 文件**在安装期间不能被移动、改名或删除**。

### 什么样的 ISO 能用

- 微软官方的 Windows 10 / 11 安装 ISO —— 可以
- 各种第三方精简版、Ghost 恢复盘 —— 要看它内部是不是标准结构
  - 有 `sources\install.wim` 或 `install.esd` 的：可以
  - 只有 `.gho` / `.esd` 分卷碎片、或者根目录直接放 `.wim` 的：**不行**
- 非 Windows 系统盘（Linux、PE 工具盘）：不行

### 索引选择

一个镜像里可能包含多个版本（家庭版、专业版、教育版……）。程序默认用**索引 1**，
但如果索引 1 是「Windows PE」或「Windows Setup」这类不能当系统用的东西，
会自动跳到第一个真正可安装的索引。

想指定装哪个版本，目前需要在源码里改 `Invoke-Install` 的 `-ImageIndex` 参数。

### ESD 和 WIM 的区别

`.esd` 就是压缩率更高的 WIM，对用户来说没有区别 —— 一样选、一样装，
只是解压时 CPU 占用稍微高一点、慢一点点。

## 常见问题

**Q：双击后闪一下就没了？**
说明自解压或提权失败。右键 `双击我-装系统.bat` → 「以管理员身份运行」试试。
还不行就去看日志：`%TEMP%\虚拟硬盘系统-年月日.log`

**Q：提示「ISO 里找不到 sources\install.wim 或 install.esd」？**
这个 ISO 不是标准 Windows 安装盘。换个镜像，或者手动把里面的 `.wim` 解出来单独选。

**Q：装了 ISO 之后光驱里一直挂着一个盘？**
正常应该自动卸载。如果异常残留，在「此电脑」里右键那个光驱 → 「弹出」即可。

**Q：找不到镜像文件？**
程序只扫本程序目录（及下两层）、上一级、下载、桌面、各盘根目录。
镜像放在深层目录时，点「浏览...」直接选。

**Q：提示"需要管理员权限"，但我点了是没反应？**
右键 `双击我-装系统.bat`，选「以管理员身份运行」。

**Q：提示"安装脚本解包失败"？**
1. 文件可能复制不完整，重新拷一份
2. 杀毒软件拦截了 `certutil` 命令，临时关掉杀软再试
3. 检查 `%TEMP%\OneKeyInstall` 目录有没有写权限

**Q：进度卡住不动？**
DISM 在解压大文件块时会停几十秒，属于正常。超过 10 分钟完全没动才需要管。
可以打开任务管理器看 `dism.exe` 是否还在占 CPU/磁盘。

**Q：装完了但开机菜单没出现新系统？**
1. 先进原系统，找到那个 `你起的名字.vhdx`（有就说明系统文件装好了，只差启动项）
2. **直接运行 `修好菜单指向-管理员运行.bat`**，它会核对菜单并补回来
3. 还不行再用 `修复启动菜单-管理员运行.bat` 重建一条
4. 想自己查：管理员 PowerShell 跑 `bcdedit /enum osloader`，看有没有
   `device  vhd=[X:]\目录\你起的名字.vhdx` 这一条
5. 都没有的话看日志：`%TEMP%\虚拟硬盘系统-*.log`、`%TEMP%\修好菜单指向-*.log`
6. 检查 `bcdedit /enum {bootmgr}` 里的 `timeout` 是不是 0 —— 是 0 的话开机会直接进
   默认系统、不显示菜单（修复工具会自动改成 10 秒）

**Q：菜单里有这个名字，一选就报 0xc000000f / 找不到文件？**
这就是菜单指向的 vhdx 路径不对。v1.13 之前的版本有个 bug：装到子目录时，
只把**文件名**写进了启动项，中间的目录被丢了。比如装到 `D:\虚拟磁盘\maimai.vhdx`，
菜单里却写成 `vhd=[D:]\maimai.vhdx` —— 这个文件根本不存在。

修：运行 `急救工具\修好菜单指向-管理员运行.bat`，几秒钟改回来，不用重装。
想看确切内容：管理员 PowerShell 跑
`bcdedit /enum osloader`，对照 `device` 那行和真实文件位置。

**Q：能装到 U 盘上吗？**
不行（v1.11 起会明确拒绝）。vhd 要在开机那一刻被固件/引导程序读到，U 盘、移动硬盘、
网络盘都可能不在或识别不到，代价是整个系统起不来。只能装到本地固定硬盘的 NTFS 分区。

**Q：能装多个新系统吗？**
能，v1.11 起是原生支持：

1. 装完第一个，关掉窗口重新打开
2. 第 ③ 步换个名字（比如「游戏系统」）
3. 位置可以一样也可以换目录
4. 装完重启，菜单里就是两条，各进各的

每个系统是独立的 vhdx，互不影响。名字会同时用作文件名和菜单文字。
同一个目录下重名会自动变成 `名字(2).vhdx`，不会互相覆盖。

卸载时在列表里按名字选，删哪个只影响哪个。

**Q：能不能把系统装到 `D:\VHD\Win11` 这样的子目录里？**
能。第 ② 步的路径框可以直接输入任意存在的目录，也能点「浏览...」选。
要求是本地固定硬盘上的 NTFS 分区，且不在 `Windows` / `Program Files` / `ProgramData` / `Users` 那些系统目录里。

**Q：新系统占多少空间？**
初始只占几十 MB（动态 VHDX），随使用增长。
上限是你设置的那个 GB 数。用满了新系统里会提示磁盘空间不足，这时需要扩容
（挂载 vhdx、用 diskpart extend，属于进阶操作）。

**Q：弹出「管道元素中的 `&` 后面的表达式生成无效的对象」？（v1.0 老问题，已修）**
根因：`Guard` 里 `return { & $Body ... }` 返回的脚本块在**执行时**才去解析 `$Body`，
那时已经离开函数作用域，`$Body` 是 `$null`。必须用 `.GetNewClosure()` 捕获：

```powershell
$handler = { param($sender, $e) ... & $Body ... }
return $handler.GetNewClosure()
```

**PowerShell 的脚本块默认延迟绑定，`return { ... }` 不会带走当前作用域的变量。**

**Q：弹出「无法将 'DefaultButton1' 转换为 'MessageBoxDefaultButton'」？（v1.1 老问题，已修）**

根因：`MessageBoxDefaultButton` 枚举里没有 `DefaultButton1`，正确的是 `Button1` / `Button2` / `Button3`。
字符串能通过 PowerShell 语法检查（因为是运行时才转换），直到弹窗那一刻才炸。

修法不只是改对名字，而是把 `MessageBox.Show` 全部收进一个强类型封装：

```powershell
function Show-Box {
    param(
        [string]$Text,
        [string]$Caption = '提示',
        [System.Windows.Forms.MessageBoxButtons]$Buttons = [System.Windows.Forms.MessageBoxButtons]::OK,
        [System.Windows.Forms.MessageBoxIcon]$Icon = [System.Windows.Forms.MessageBoxIcon]::Information,
        [System.Windows.Forms.MessageBoxDefaultButton]$Default = [System.Windows.Forms.MessageBoxDefaultButton]::Button1
    )
    return [System.Windows.Forms.MessageBox]::Show($Text, $Caption, $Buttons, $Icon, $Default)
}
```

**顺便挖出第二个坑**：`GetNewClosure()` 只捕获**变量**，不捕获**函数定义**。
`Guard` 返回的闭包在新的会话状态里跑，连脚本级 `function Show-Box` 都解析不到
（实测闭包内 `Get-Command Show-Box` 返回 `$null`），结果错误处理路径自己又崩一次。
正确做法是把函数体先变成变量：

```powershell
$boxFn = (Get-Item function:Show-Box).ScriptBlock   # 变成变量，随闭包一起捕获
# 闭包内：
& $boxFn -Text $msg -Caption '操作出错' -Buttons ... -Icon ...
```

**Q：弹出「设置字符串格式时出错：索引必须大于或等于零」？（v1.0 老问题，已修）**
```powershell
# 错：方法调用参数按逗号切分，-f 只吃到 $stamp，格式串却有 3 个占位符
$log.AppendText('[{0}] {1}{2}' -f $stamp, $m, [char]13 + [char]10)

# 对：先生成整行
$line = '[' + $stamp + '] ' + $m + [char]13 + [char]10
$log.AppendText($line)
```
**命令位置的 `-f` 能吃整个逗号列表，方法调用括号里的 `-f` 不能。**

## 技术原理（给想了解的人）

```
0. （仅 .iso）Mount-DiskImage   挂载 ISO，取出 sources\install.wim 或 install.esd
1. New-VHD 或 diskpart          在当前系统里创建一个动态扩展的 .vhdx 文件
2. Mount-VHD 或 attach vdisk    挂载成一个虚拟磁盘（就像插了一块新硬盘）
3. diskpart                     在里面建 GPT 分区表 + **一个** NTFS 主分区（不建 ESP）
4. dism /Apply-Image            把镜像展开到该分区（自动跳过 WinPE 类索引）
5. bcdedit /store               在**物理磁盘的 ESP** 的 BCD 里加一条启动项：
                                  device  = vhd=[D:]\NewSystemDisk.vhdx
                                  osdevice= vhd=[D:]\NewSystemDisk.vhdx
                                  path    = \Windows\system32\winload.efi
6. Dismount-VHD / detach vdisk  卸载
7. （仅 .iso）Dismount-DiskImage 卸载 ISO（放在 finally，成功失败都执行）
```

没有 Hyper-V 模块的机器上，第 1、2、6 步自动降级成 `diskpart create/attach/detach vdisk`。

**为什么 vhdx 里只能有一个分区**：这叫 native boot（原生引导虚拟硬盘），是 Windows
自己支持的一种启动方式。bootmgr 拿到 `vhd=[D:]\xxx.vhdx` 后，只会把该虚拟磁盘的
**第一个分区**当作启动分区。所以里面多一个 ESP，bootmgr 就会认错分区，起不来。

**为什么启动项要写在物理 ESP 上**：UEFI 固件启动时只扫物理磁盘上的 EFI 系统分区，
按 `\EFI\Microsoft\Boot\bootmgfw.efi` 加载 Windows 启动管理器。它不认识 vhdx 内部的分区，
也不会进去找。所以「把启动文件写进 vhdx 里的 ESP」这条路走不通 —— 这正是 v1.3 的失败原因。

**关于「不改动原系统」这句话的准确性**：
- 分区表、系统文件、原有启动项：**一个都没动**
- 但确实往物理 ESP 的 BCD 存储里**新增了一条记录**（不改原有记录、不覆盖 `bootmgfw.efi`）
- 改动前的 BCD 会备份成 `D:\bcd-backup-<时间>.bcd`，卸载时会删掉新增的那条记录

镜像格式的处理逻辑收敛在一个函数 `Resolve-RealImage` 里：

| 输入 | 输出给 DISM 的路径 | 需要收尾 |
|---|---|---|
| `x.wim` / `x.esd` | 原路径 | 无 |
| `x.iso` | `G:\sources\install.esd`（挂载后解析） | 卸载 G: |

这样 `Invoke-Install` 里只认一个 `$realImage`，不用到处判断格式。

## 限制和注意事项

### 硬性要求

| 项目 | 要求 | 不满足会怎样 |
|---|---|---|
| 当前系统 | Windows 10 1607 以上 / 64 位 | 无法运行 |
| 权限 | 管理员 | 弹不出权限窗口就退出 |
| 存放分区 | NTFS、本地固定盘、剩余 ≥ 大小+5GB | 盘符按钮里看不到该分区 |
| 存放分区（补充） | 系统盘（C:）也能放，单盘机器就靠它 | 会占走系统空间，装在 C 盘时界面会黄字提醒 |
| 目标机状态 | **能正常开机进 Windows** | 工具用不了，只能用 U 盘/PE |

### 已知限制

**1. 新系统是"并存"而不是"替换"**
原 C 盘仍然存在、仍然占着空间。这是在不进 PE 的前提下唯一能做到的方式。
真要彻底替换，只能进 PE 把 C 盘格式化 —— 那就回到 U 盘方案了。

**2. 首次进新系统可能要求激活**
镜像里的授权状态会带过来。如果原来没激活，新系统也没激活。
（可以用原来的密钥激活，或者本来就是数字权利的话会自动认）

**3. 分配到的盘符可能变**
新系统进去后，原来的 C 盘可能显示成 D 盘、E 盘之类。这是正常的，因为引导卷不同。

**4. 休眠 / 快速启动**
如果原系统开了「快速启动」，有时会导致启动菜单不显示。遇到的话在
「控制面板 → 电源选项 → 选择电源按钮的功能」里关掉「启用快速启动」。

**5. Secure Boot（安全启动）**

新系统的 `winload.efi` 来自镜像。如果镜像是原版 Windows，微软签名有效，Secure Boot 开着也能过。
如果镜像被改过（删驱动、改引导、做精简），`winload.efi` 的签名可能失效，
开机时会报 `0xc0000428`（数字签名无法验证）之类的错误。

遇到这种情况：进 BIOS 临时关掉 Secure Boot 就能启动。
本工具无法检测你的 Secure Boot 状态（需要管理员权限，且脚本里我没加这一步）。

**6. 机器上本来就有别的系统（双系统 / 多系统）**

本工具在原有系统之上**再加一项**，不动别人的启动项。具体行为：

| 场合 | 做法 |
|---|---|
| 复制谁的启动项 | 复制 `{current}`（你正在跑的这个），不用 `{default}` —— 多系统机器上 `{default}` 可能是另一个系统，复制它会得到一个根本指错的条目 |
| 会不会改你原来的菜单超时 | 只在 `timeout=0` 时把超时提到 10 秒（否则看不到菜单）；你原来是 30 秒就仍是 30 秒，不会被缩短 |
| 菜单描述重名 | 如果已有同名条目（比如两块盘各装了一份），自动补盘符变成「Windows 10 专业版（虚拟系统 D:）」 |
| 卸载时 | 只删指向**这一个 vhdx 完整路径**的条目；两块盘都有 `NewSystemDisk.vhdx` 也不会误删另一份 |
| 卸载后菜单 | 用 `bcdedit /deletevalue` 恢复成「未设置」：单系统机器照样直接进系统，**多系统机器原来的菜单正常保留** |

日志里会写一行 `机器上已有 N 个启动项（多系统）：本次只新增一项，原有条目不动`，
可以在日志里核对。

唯一需要人工确认的边界：如果你**手动改过 vhdx 所在盘符**（比如从 D: 变成了 F:），
卸载时的兜底匹配会退化成「只比文件名」，此时若两块盘上都有同名文件，日志里会打
`警告：...可能包含别的盘上的同名系统`，请先核对再删。

**7. 分发合规**
如果要把这个镜像和工具发给别人，注意镜像是你机器上的系统克隆，可能包含：
- 你的用户数据、浏览器记录、账号凭据
- 商业软件授权（一般不允许转移）
- 原机器的 OEM 授权绑定

**建议在分发前对镜像跑一次 sysprep /generalize**，或者至少清干净个人数据。

## 日志 / 备份 / 报告在哪

**从 v1.29 起，安装过程中产生的所有附属文件都收在一个子目录里**，跟着虚拟磁盘走：

```
D:\虚拟磁盘\虚拟硬盘系统-日志\          ← 虚拟磁盘装在 D:\虚拟磁盘 时
D:\虚拟硬盘系统-日志\                    ← 虚拟磁盘直接装在盘根时
```

里面会有这些：

| 文件 | 是什么 |
|---|---|
| `虚拟硬盘系统-YYYYMMDD.log` | 安装日志：每步时间、命令输出、DISM 退出码。出问题先看这个 |
| `bcd-backup-YYYYMMDD-HHmmss.bcd` | 装/修之前备份的 BCD，要回滚就用它 |
| `修复启动菜单报告.txt` | 「修复启动菜单」跑完的报告 |
| `新系统诊断.txt` / `显卡诊断.txt` | 对应急救工具跑出来的报告 |

虚拟磁盘旁边只会剩两样：**vhdx 本身**，和它的 **`xxx.boot.txt`**（安装器写的状态文件，
记录启动项 GUID，卸载/修复都要靠它，所以必须跟 vhdx 放在一起）。

> v1.29 之前，日志在 `%TEMP%`、BCD 备份直接丢在 vhdx 旁边，而且 `bcdedit /export`
> 还会额外生成 `.bcd.LOG` / `.LOG1` / `.LOG2` 三个伴生文件 —— 装在盘根就糊一片。
> 这些老文件没有自动搬走/删除，要清的话跑
> `急救工具\清理安装残留-管理员运行.bat`，最后一步【D】会把它们列出来，
> 输入 y 才删（只删 `.bcd.LOG*`，`.bcd` 备份本身保留）。

### 显卡「空 GPU」定位（已实测，2026-11-04）

对照用户在新系统里跑出来的 `D:\显卡诊断.txt` 和主机侧数据：

| 系统 | 显示适配器 |
|---|---|
| 新系统（Win10 19045） | GameViewer 虚拟显示器、RTX 3070、Intel 核显 + 3 个 NVIDIA 幽灵（GTX 960 ×2、GTX 660） |
| 主机（Win11 26200） | GameViewer + MuMu 两个虚拟显示器、RTX 3070、Intel 核显 |

- `Win32_VideoController` 只枚举**活动**适配器，幽灵设备不在其中 ⇒ 空 GPU 不可能是幽灵卡
- 两个虚拟显示器的 `Service` 都是 `WUDFRd`（用户模式驱动框架），没有真实 DX 引擎
- 分类逻辑在主机实测：GameViewer / MuMu 判为「虚拟显示器」，RTX 3070 / Intel 判为「在用」，
  5 条断言全 PASS
- **决定性证据**：`pnputil /remove-device` 传一个**完全不存在**的设备 ID 也返回**退出码 0**
  ⇒ v1.0 靠 `$LASTEXITCODE -eq 0` 判「删除成功」完全无效，那份「成功 3 个」的报告不可信
- IDD 过滤规则在本机 164 个第三方 INF 上实测：只命中 `oem18.inf`(GameViewer) 与
  `oem65.inf`(MuMu)，NVIDIA 与 Intel 的 INF 不命中，无误伤

### v1.2 修复：创建虚拟磁盘失败（diskpart 路径编码，已实测）

报错原文：

```
DiskPart 遇到错误: 文件名、目录名或卷标语法不正确。
```

**根因**：生成 diskpart 脚本文件时用了 ASCII 编码，而 ASCII 编码器会把**所有非 ASCII 字符替换成 `?`**。
VHD 文件名当时是 `新系统.vhdx`，写到脚本里就变成：

```
create vdisk file="D:\???.vhdx" maximum=51200 type=expandable
```

实测确认的字节（Build 26200）：

```
ASCII 写出：44 3A 5C 3F 3F 3F 2E 76 68 64 78   → D:\???.vhdx
正确 GBK：  44 3A 5C D0 C2 CF B5 CD B3 2E ... → D:\新系统.vhdx
```

DiskPart 找不到 `???.vhdx` 就报「文件名、目录名或卷标语法不正确」。
更误导的是：那个问号名字的文件**已经被创建出来了**，所以 `Test-Path` 查原路径失败，
脚本却以为自己把虚拟磁盘挂上了 —— 报错信息看着像别的问题。

**修复**：

1. 新增 `Get-AnsiEncoding`，读注册表 `Nls\CodePage\ACP` 拿当前系统代码页（中文 = 936），
   所有 diskpart 脚本文件改用这个编码写，中文路径不再被替换成 `?`
2. 新增 `Invoke-Diskpart` 统一入口，所有 diskpart 调用收敛到一处，顺便修掉两个老问题：
   - `$LASTEXITCODE` 在 PowerShell 里调 diskpart **常常是 $null**，判断不可靠 → 改成解析输出文本
     （中英文错误串都匹配：`DiskPart 遇到错误` / `DiskPart has encountered an error`）
   - diskpart 脚本行尾统一 CRLF（手工拼接，不赌 `AppendLine`）
3. VHD 文件名 `新系统.vhdx` → **`NewSystemDisk.vhdx`**（纯 ASCII，双保险）。
   卸载工具同时认新旧两个名字，老版本装过的照样能卸。
4. 分区卷标 `新系统` → `NewSystem`，同理。
5. **扫描范围收紧**：原来会把每个盘的根目录都扫进去，`Downloads` 里放个 Kali ISO 就会被列成
   「有效=False 解压后 0 GB」吓人。现在只扫「程序所在目录 / 其上级 / 桌面 / 下载」，
   并且文件名含 kali/ubuntu/debian 等字样的 ISO 直接不列出。放别处可以用「浏览」按钮指定。
6. **修掉一个「镜像列表永远是空」的 bug**：控制台模式下只传了 `-SearchRoot`，
   而大众双击时根本没这个参数 → `OriginDir` 被忽略 → 明明 wim 就在旁边还是显示「（无）」。
   现在没显式指定时会自动回落到 OriginDir / 脚本目录。

| 测试项 | 结果 |
|---|---|
| ANSI 编码写出含中文的路径 | 无 `0x3F` 问号，`新系统` → `D0 C2 CF B5 CD B3`，行尾 `0D 0A` |
| diskpart 输出解析（中文错误 / 英文错误 / 正常） | 3/3 判对 |
| 源码裸 `& diskpart` 调用 | 只剩 `Invoke-Diskpart` 内那 1 处 |
| 源码 ASCII 写文件 | 只剩 WIM magic 比对那 1 处（正确用途） |
| 解包后 SHA256 与源码一致 | True |
| 三种参数组合找镜像 | `-SearchRoot` / `-OriginDir` / 两者都给 → 都能列出 maimai3.wim |
| 语法 / `-f` 隐患 | 0 / 0 |

### v1.3 修复：bcdboot 报 BFSVC 0x7b（已确认根因，未在本机复现）

报错原文：

```
BFSVC Error: ServicingBootFiles failed. Error = 0x7b
```

**好消息**：日志里这一行是关键证据 ——

```
[19:13:59] [INFO] DISM 退出码: 0
[19:13:59] [INFO] 配置启动菜单...
[19:13:59] [ERROR] 失败: BFSVC Error: ServicingBootFiles failed. Error = 0x7b
```

`DISM 退出码 0` 意味着 **19GB 的镜像已经完整写进虚拟磁盘了**，
耗时约 2 分钟（19:11:55 → 19:13:59）。出问题的只有最后一步「注册启动项」。
`0x7b` = `ERROR_INVALID_NAME`，报错里的 `ServicingBootFiles` 是 bcdboot 内部处理启动文件的服务例程。

**根因**：原来调用的是

```
bcdboot E:\Windows /s T: /f UEFI /d /v
```

`/d` 的作用是「保留现有默认启动项」，但它会让 bcdboot 连带走 **WinRE（恢复环境）注册流程** ——
反汇编 `bcdboot.exe` 可以确认它会加载 `REAGENT.DLL` 并处理 `EFI\Microsoft\Recovery`。
而全新虚拟磁盘里既没有 WinRE，也没有 `\Recovery\WindowsRE\winre.wim`
（本机 `C:\Windows\System32\Recovery` 下只有 `ReAgent.xml`，`WinRELocation` 指向的
`\Recovery\WindowsRE` 目录根本不存在 —— 说明这台机器的 WinRE 早就被删了）。
路径解析失败 → `ERROR_INVALID_NAME (0x7b)`。

**修复**：

1. **去掉 `/d`**（核心修改）
2. 加**多级回退**：`/f UEFI` → `/f UEFI /v` → `/f ALL`，每级都写日志，看得出是哪一级过的
3. 失败时的报错文案改成说人话，并明确告知「系统文件其实已经写好了」
4. **失败不再无条件删 vhdx**：如果系统文件已经应用完成（DISM 成功）只是引导没注册上，
   保留虚拟磁盘 —— DISM 那 2 分钟不该白费，而且删了重跑还是同样的错

**我没能在本机复现验证**（如实说明）：
我用一个临时 4GB vhdx 造了对比实验（带 `/d` / 不带 `/d` 各跑一次），
但工具环境是**非管理员**，`diskpart` 直接被拒（`请求的操作需要提升`），
实验没能跑成，临时文件已清理。所以 `/d` 是根因这一点，依据是：

- 官方文档对 `/d` 的描述（保留现有默认启动项 → 需要既存的 BCD 上下文）
- `bcdboot.exe` 里确实存在 `REAGENT.DLL` 与 `EFI\Microsoft\Recovery` 相关路径
- 本机 WinRE 确认缺失，而新建 vhdx 里必然也缺失

如果新版本仍然报同样的错，请把日志里这几行发我：

```
bcdboot [UEFI] => exit=...
bcdboot [UEFI-verbose] => exit=...
bcdboot [ALL] => exit=...
```

三级各自的返回码能直接定位是哪一环卡的。

### v1.4 修复：装完重启没有启动菜单（根因确定，有直接证据）

**现象**：v1.3 报「安装完成」，但重启后开机菜单里根本没有新系统，直接进原系统。

**这一版推翻了我之前的判断。** 上一节说 `/d` 是根因、去掉就好 —— 去掉之后确实不再报
`BFSVC 0x7b` 了，`bcdboot` 返回 `exit=0 已成功创建启动文件`，但它**依然什么用都没有**。
`0x7b` 只是把一个更底层的问题暴露出来的副作用。

日志里的决定性一行：

```
[19:22:27] [WARN] ESP 盘符分配失败: The requested access path is already in use.
[19:25:01] [INFO] bcdboot [原系统引导] => exit=0  已成功创建启动文件。
```

第一行说明：脚本给**虚拟磁盘内部的 ESP** 分配盘符 `T:` 失败了，于是 `$espLetter` 为空，
`bcdboot` 落到兜底分支 —— 往 `$env:SystemDrive`（也就是 `C:\`）用 `/f ALL` 写。

第二行 `exit=0` 是**假成功**。证据是 C 盘根目录凭空多出两个目录，创建时间正好是那一刻：

```
C:\EFI\Microsoft\Boot\  ← BCD、bootmgfw.efi ……  创建于 19:25
C:\Boot\                ← BCD、bootvhd.dll ……   创建于 19:24
```

**UEFI 固件只读磁盘上的 EFI 系统分区（ESP），永远不会去读 `C:\EFI`。**
所以文件确实写出来了，但写在了固件不看的地方，等于没做。

**真正的根因是结构性的**：

| 位置 | v1.3 的做法 | 为什么不行 |
|---|---|---|
| 启动文件 | 写进 **vhdx 内部的 ESP** | 固件只扫**物理磁盘**的 ESP，不会进 vhdx 里找 |
| vhdx 分区 | ESP(260MB) + NTFS 两个分区 | native boot 要求 vhdx **只有一个分区**，bootmgr 按 `vhd=` 定位时只认第一个分区 —— 那个空 ESP 会顶掉真系统 |
| 物理 ESP | 完全没动过 | 真正的开机菜单在这里，没被写过 |

本机磁盘实际情况（只读查询得到）：

```
Disk 0  SAMSUNG MZVL21T0HCLR  953.9GB
  Part1  ESP        300MB   GUID c12a7328-...   无盘符   ← 开机菜单真正在这里
  Part2  MSR         16MB
  Part3  NTFS       204GB   C:  系统
  Part4  NTFS       771GB   D:  数据
```

**v1.4 的做法（native boot 的标准形态）**：

1. vhdx 里**只建一个 NTFS 分区**，不再建 ESP
2. 用 DISM 把系统应用到这个分区（和以前一样）
3. **不再用 `bcdboot`**。改成操作**物理 ESP 上的 BCD**：
   ```
   bcdedit /store S:\EFI\Microsoft\Boot\bcd /copy {default} /d "Windows 10（新系统）"
   bcdedit /store ... /set {新GUID} device   vhd=[D:]\NewSystemDisk.vhdx
   bcdedit /store ... /set {新GUID} osdevice vhd=[D:]\NewSystemDisk.vhdx
   bcdedit /store ... /set {新GUID} path     \Windows\system32\winload.efi
   ```
4. 打开开机菜单：`displaybootmenu Yes`；若原 `timeout=0` 则改成 10 秒
   （不改的话开机会直接进默认系统，根本看不到选项 —— 这也是「没菜单」的一种可能）

**安全设计**（改引导这种事必须留退路）：

- 改之前先把 ESP 上的 BCD 备份成 `D:\bcd-backup-<时间>.bcd`
- 任何一步失败自动把备份还原回去
- **不覆盖** ESP 上的 `bootmgfw.efi`（避免用旧版引导程序替换新版，把原系统也搞挂）
- **不改** 默认启动项，原系统仍是默认；菜单 10 秒超时后自动进原系统
- 所以即使新条目完全坏的，你也只是看到一个菜单，不选它就回去了

**不用重装也能修**：新增了 `修复启动菜单-管理员运行.bat`，专门处理「系统文件已经装好、
只差注册启动项」这种情况。它会：

1. 挂载现有的 `D:\NewSystemDisk.vhdx`
2. 如果里面有 ESP 分区 → 删掉，让它变成单分区（**系统文件不动**）
3. 在物理 ESP 的 BCD 里加启动项
4. 清理 `C:\EFI`、`C:\Boot` 两个垃圾目录
5. 卸载 vhdx、释放盘符

全程约 30 秒，不用重新 DISM 那 2 分钟。

**已在本机验证的部分**：

| 项目 | 结果 |
|---|---|
| 找到物理 ESP | ✅ Disk 0 Part 1，300MB，GUID 匹配 |
| device 字符串生成 | ✅ `vhd=[D:]\NewSystemDisk.vhdx` |
| 候选盘符可用性 | ✅ `S:` 空闲 |
| 非管理员时 bcdedit 行为 | ✅ 明确报「拒绝访问」，脚本会正确判定失败 |
| 脚本语法 / 打包一致性 | ✅ 三个脚本 0 错误，bat 解包 SHA256 与源文件一致 |
| 修复脚本走到管理员检查 | ✅ 日志正常，在正确位置拦下 |

**仍是推断、需要你实机确认的一点**：

删掉 vhdx 内部的 ESP 后，NTFS 分区会不会自动变成「分区 1」。理论上 Windows 的
`delete partition` 会把 GPT 分区项紧凑重排，但这一点我这边非管理员，改不了分区表，
没法实测。脚本会把结果写进日志：


如果这一行显示的不是 `1`，说明有分区空洞，bootmgr 可能仍然找不到系统 ——
那就直接重跑 `双击我-装系统.bat`（v1.4 从头就是单分区，不存在这个问题）。


### v1.5 修复：备份 BCD 时撞共享冲突（有直接报错证据）

**现象**：双击「修复启动菜单」后，日志里这一步直接失败：

```
[19:38:59] [INFO] BCD: S:\EFI\Microsoft\Boot\bcd
[19:38:59] [ERROR] 失败: 文件"S:\EFI\Microsoft\Boot\bcd"正由另一进程使用，因此该进程无法访问此文件。
```

**根因**：v1.4 虽然思路对了（启动项写物理 ESP），但做法错了——它先给物理 ESP 挂了个
盘符 `S:`，然后把 `S:\EFI\Microsoft\Boot\bcd` 当**普通文件**去复制备份。而当前正在运行的
系统自己就握着这个 BCD 的句柄（它就是靠这份 BCD 启动起来的），任何文件级的复制 / 覆盖
都会被系统拒绝，报「正由另一进程使用」。

也就是说：**方向对了，但用了文件系统的手去改一个系统正在占用的引导配置，必然撞锁。**

**v1.5 的做法：走 BCD 的 API，不碰文件**

`bcdedit` 有一个关键特性：**不带 `/store` 参数时，它操作的是「活动 BCD 存储」**——就是当前
系统实际启动用的那一份，它本来就存在物理 ESP 上。改它等价于改物理 ESP，但全程走的是
引导配置的专用 API，不经过文件句柄，所以：

- 不需要给 ESP 挂盘符
- 不需要读写 `S:\EFI\Microsoft\Boot\bcd` 这个文件
- 不会再有「正由另一进程使用」的冲突

关键改动：

| 环节 | v1.4（错） | v1.5（对） |
|---|---|---|
| 定位 BCD | 给物理 ESP 挂盘符，找 `S:\...\bcd` 文件 | 直接用活动存储（bcdedit 不带 /store） |
| 备份 | `Copy-Item` 复制 bcd 文件 | `bcdedit /export D:\bcd-backup-*.bcd` |
| 还原（失败时） | `Copy-Item` 复制回去 | `bcdedit /import D:\bcd-backup-*.bcd` |
| 加条目 / 改超时 | `bcdedit /store S:\...\bcd /set ...` | `bcdedit /set ...`（默认活动存储） |

命令对照：

```
# 备份（v1.4 是 Copy-Item，会撞锁）
bcdedit /export D:\bcd-backup-20261103.bcd

# 加启动项
bcdedit /copy {default} /d "Windows 10（新系统）"    → 拿到新 GUID
bcdedit /set {新GUID} device   vhd=[D:]\NewSystemDisk.vhdx
bcdedit /set {新GUID} osdevice vhd=[D:]\NewSystemDisk.vhdx
bcdedit /set {新GUID} path     \Windows\system32\winload.efi
bcdedit /set {bootmgr} displaybootmenu Yes
bcdedit /set {bootmgr} timeout 10

# 万一要还原
bcdedit /import D:\bcd-backup-20261103.bcd
```

**顺带说明**：`/export` 备份如果失败（极少数机器），脚本**不再因此中断**——因为后面只做
「新增一条启动项 + 改菜单超时」这两件用 `bcdedit` 就能反向撤回的事，文件级备份只是多加
一层保险。真正关键的还是「新增前先 `/export` 导出」这个动作本身，一旦 `vhd=` 写错，随时
能 `/import` 恢复。

**修复工具同步升级到 v1.1**，主安装程序升到 **v1.5**。两者的 bcdedit 全部改为活动存储。

**这次是有直接报错证据的**：你截图的那条「正由另一进程使用」正是 v1.4 的 `Copy-Item`
备份那一步，日志时间戳 19:38:59 对得上。v1.5 已经把这条路径彻底换掉。


### v1.6 修复：vhd= 被偷换成 partition=E:（有直接日志证据）

**现象**：修复工具这次跑得很远——文件锁没了（v1.5 修好了），备份成功、复制启动项成功、
`/set` 三条全部返回「操作成功完成」，但最后**读回校验**拦下了：

```
[19:48:15] bcdedit set [device vhd=[D:]\NewSystemDisk.vhdx] => exit=0  操作成功完成。
[19:48:16] bcdedit verify [/enum {9b824bfd-...}] => device partition=E: path \Windows\...
[19:48:16] 条目校验: 含 vhd= => False
```

**根因**：执行 `/set device vhd=[...]` 那一刻，虚拟磁盘还处于**挂载状态**（脚本是挂载它
来删分区的）。bcdedit 解析 `vhd=[D:]\NewSystemDisk.vhdx` 时发现这个虚拟盘正连着，就把
设备**直接写成了它内部卷的 `partition=E:`**，而不是保留 `vhd=` 文件引用。返回值还是
「操作成功完成」——又一个假成功。

这样的条目重启后必然失败：vhdx 平时是不挂载的，bootmgr 指着一个不存在的卷。

**修法**：先卸载 vhdx，再做所有 BCD 操作。分区修完、系统文件检查完就 `detach vdisk`，
后面的备份 / 复制 / `/set` / 校验全程在「vhdx 未挂载」状态下进行。这是 native boot 的
标准姿势——`bcdedit /set device vhd=` 必须在虚拟盘未连接时执行。

安装程序（v1.6）同样修了：DISM 应用完镜像、检查完分区号后，先卸载 vhdx 再调
`Install-BootEntry`。

**这条链路现在的状态**：文件锁（v1.5 修）、假成功 exit=0（v1.6 修）都已实测排除，
剩下就是 `/set` 在卸载状态下写入并读回验证 `vhd=` 这最后一步。


### v1.7 修复：卸载后残留 ESP 盘符（S: 等，有直接证据）

**现象**：卸载完新系统，资源管理器里却多出一个盘符（常见 `S:`），点进去是空的或提示无法访问。

**根因**：早期版本的「修复启动菜单」工具（v1.0）为了改物理 ESP 上的 BCD，会先给那个
EFI 系统分区临时挂一个盘符（挑空闲的 S/R/Q/P…），用完才摘。但那个版本在**备份 BCD 撞锁
失败**时提前退出了，摘盘符的收尾代码没跑到，盘符就残留下来了。之后 v1.5 起改成走活动
BCD 存储、不再需要盘符，但早期挂上的那次一直没人清理。

本机实测确认：
```
S: -> Disk0 Part1  Type=System  300MB  GptType=c12a7328-...（EFI 系统分区）
```
`S:` 就是物理 ESP 本身，只是多了个不该有的访问路径，**没有任何数据问题**，也不影响启动。

**修法**：
1. 卸载工具升到 **v1.3**：删完 vhdx 后自动扫一遍所有分区，凡是「EFI 系统分区却占着
   非系统盘符」的残留，统统摘掉（`Remove-PartitionAccessPath`，只去访问路径、不动数据）。
2. 另配了独立的 `清理ESP盘符-管理员运行.bat`，双击即清，专门处理已经残留的盘符。

**怎么手动清**（不想要工具的话）：管理员 PowerShell 跑
```powershell
Remove-PartitionAccessPath -DiskNumber 0 -PartitionNumber 1 -AccessPath "S:"
```
（把 0 / 1 / S 换成实际值。或者磁盘管理里右键那个 300MB 的 EFI 分区 → 更改驱动器号 → 删除。）


### v1.8 修复：卸载后开机菜单还在（有直接证据）

**现象**：卸载完新系统，启动选项确实没了，但开机菜单还弹出来，没直接进系统。

**根因**：卸载脚本只还原了 `timeout`，没还原 `displaybootmenu`，而且还原逻辑是硬编码判断
「`timeout==0` 才还原」。

实际链条是这样的：
1. 「修复启动菜单」工具为了让你能看到菜单，会执行
   `bcdedit /set {bootmgr} displaybootmenu Yes`；只有当原 `timeout=0` 时才把 timeout 改成 10 秒。
2. 你的原系统 `timeout=30`（不是 0），所以工具**只改了 `displaybootmenu`，没动 timeout**。
3. 卸载时，脚本判断 `if ($origTimeout -eq '0')` 不成立 → 什么都不还原 →
   `displaybootmenu` 一直停在 `Yes` → 开机菜单就还在。

状态文件里其实**记了 `OrigDisplayMenu` 这个字段**，但卸载脚本根本没读它，等于白记了。

**修法**：
1. 卸载工具升到 **v1.4**：读取 `OrigDisplayMenu` 字段，只要删掉了启动项，就**无条件**把
   `timeout` 和 `displaybootmenu` 都还原成状态文件里记下的原始值，不再硬编码判断 timeout==0。
2. 另配了 `还原启动菜单-管理员运行.bat`，双击即用，专门处理「已经卸载但菜单还残留」的情况——
   它会把 `displaybootmenu` 设为 No、`timeout` 设为 0，开机直接进默认系统。

**怎么手动清**（不想要工具的话）：管理员 PowerShell 跑
```powershell
bcdedit /set {bootmgr} displaybootmenu No
bcdedit /set {bootmgr} timeout 0
```
（`timeout 0` 表示不等待、直接进默认系统；想要菜单留 5 秒就把 0 换成 5。）


### v1.9：一轮代码审查，修掉 8 处隐患（2 处会丢数据）

这一版不是「又报了新错」，而是对整个工具做了一次静态审查，把潜在事故点提前拆掉。

#### P0：会造成数据丢失

**① 目标 vhdx 已存在时，报完错顺手把它删了**

预检发现同名文件就 `throw`「已经装过一次了」，然后落到统一的 catch 回滚逻辑。
而回滚的条件是 `$bcdTriesReached`（是否走到过注册启动项）——这时它还是 false，
于是判定「不需要保留」，**把用户已经装好、可能正在使用的那个系统整个删掉**。
提示语还写着「请先运行卸载工具」，与实际行为完全相反。

修法：新增 `$createdHere` 标志，只有在**本次运行真正创建过** vhdx 时才允许回滚删除。
删除条件从 `if (-not $keepVhd)` 改为 `if (-not $keepVhd -and $createdHere)`。

**② `diskpart clean` 可能落到真实物理磁盘上**

挂载 vhdx 后要找出它的磁盘编号。原来按 `Location` 匹配 vhdx 文件名，匹配不上时
退到「容量与目标值相差 64MB 以内、且非系统盘」——紧接着就是 `select disk` + `clean`。
机器上只要恰好有一块同容量的盘（小 SSD、U 盘、用户自己另一个 VHD），就会把整块盘的
分区表清掉。

修法：删掉容量兜底，改用 `BusType = 'File Backed Virtual'`（vhdx 挂载后特有的总线类型，
物理盘绝不可能是它）逐级判定；全都判不出来就**报错列出现有磁盘让用户介入，绝不猜**。

#### P1：功能缺陷

**③ 卸载的兜底检索在中文系统上永远不生效**

`bcdedit /enum osloader /v` 的输出跟随系统语言。中文 Windows 输出的是「标识符」「描述」，
而代码只匹配 `identifier` / `description`。结果只有状态文件里的 GUID 能删，
一旦 `.boot.txt` 丢了（手动删、写状态失败），启动项就再也删不掉。
修法：正则改成 `(?:identifier|标识符)` / `(?:description|描述)`。

**④ v1.8 声称修好的「菜单残留」，在最常见的情况下依然没修好**

这一条是上一版修复的遗漏，也是你实际反馈的症状根源：
BCD 里**从来没设过** `displaybootmenu` 时，`/enum` 输出里根本不会有这一行（默认就是 No）。
于是安装时记下的「原值」是空字符串 → 状态文件写空 → 卸载时 `if ($origDisplay -ne '')`
不成立 → 跳过还原 → 安装时设的 `Yes` 永远留着。

修法（两头都堵）：
- 安装端：读不到就落成 `'No'`（「没设过」的语义本来就等于 No），状态文件不再写空值
- 卸载端：即使原值为空，也**显式设回 No**，而不是跳过

> v1.10 起这条又细化了一次：硬设 `No` 在多系统机器上会把用户原来的双系统菜单一起关掉
> （开机直接进默认系统，另一个系统选不到）。现在改为 `bcdedit /deletevalue` 恢复「未设置」，
> 单系统照旧不弹菜单，多系统菜单保留。状态文件新增 `OrigDisplayMenuSet=0/1` 区分
> 「原本没写过」和「原本显式写 No」。

**⑤ 摘 ESP 盘符传错了参数形式**

`Remove-PartitionAccessPath -AccessPath "S:"` 少了尾部反斜杠——`-AccessPath` 要的是卷访问
路径（`S:\`），传 `S:` 会被判参数无效，而 catch 只记一行日志，盘符没摘掉用户却以为清了。
修法：统一改用 `-DriveLetter $dl`（`Release-EspLetter` 一直用的就是正确形式）。

**⑥ 主安装按钮是唯一没被 Guard 包裹的事件**

其他事件都用 `(Guard 'xxx' {...})` 包了一层，异常会变成可读弹窗。唯独「开始安装」是裸的，
一旦在 try 之外抛错就退到 WinForms 的「未处理异常」黑框，按钮可能永久变灰。
修法：`$btnGo.Add_Click((Guard '开始安装' { ... }))`。

**⑦ 失败提示与实际行为矛盾**

原来固定写「失败的虚拟磁盘文件已自动清理」，但 BCD 失败时是**刻意保留** vhdx 的。
修法：根据异常消息判断实际走了哪条路径，分别提示「已清理」或「已保留，可只补注册启动项」。

**⑧ DISM 的读流方式有死锁隐患**

- 只读 stdout、不读 stderr，且 stderr 要等主循环结束才 `ReadToEnd()`。
  DISM 往 stderr 写满管道缓冲区（约 4KB）后会阻塞，脚本还在等 stdout 的下一行 → 死锁。
- `ReadLine()` 要等 `\n`，而 DISM 的进度是用 `\r` 原地刷新的 → 进度条长时间停在 12%。

修法：
- stderr 立刻用 `ReadToEndAsync()` 在后台读走
- stdout 改成逐字符读，`\r` 和 `\n` 都当作一行结束

### 重要：不再依赖 Hyper-V 模块

原版用了 `New-VHD` / `Mount-VHD`，这两个命令属于 **Hyper-V PowerShell 模块**，
很多机器（包括我这台 Win11）根本没装，会直接报"无法识别 New-VHD"。

现在改成**双路径**：

| 路径 | 条件 | 命令 |
|---|---|---|
| 快路径 | 有 `New-VHD` | `New-VHD` + `Mount-VHD`，能直接拿到磁盘编号 |
| 兜底路径 | 没有 Hyper-V 模块也能用 | `diskpart` 的 `create vdisk` / `attach vdisk` / `detach vdisk` |

`diskpart` 是系统自带的，Windows 8 / Server 2012 以上都支持 vhdx。
程序启动时会先检查，两条路都不通时给出明确提示，而不是崩溃。

以下环节是**按官方文档和本机只读探测写的、逻辑上正确，但没能在本机实测**：

| **`bcdedit /store` 往物理 ESP 写条目** | 同上，`bcdedit` 直接报「拒绝访问」 |

### v2.0 修复：DISM 卡死在 12%（v1.7 自己引入的死锁，有实测证据）+ 虚拟磁盘冒出 2 个分区

#### 现象（2026-11-04 12:00 那次安装）

进度条停在 12%、「恢复系统文件」那行字不动，等了 11 分钟一点变化都没有。
实测采样三次，拿到的是硬证据：

| 指标 | 12:04 | 12:07 | 12:14 |
|---|---|---|---|
| `dism.exe` 累计 CPU | 51.72s | 51.72s | 51.72s |
| 目标盘已用 | 11.75 GB | 11.75 GB | 11.75 GB |
| `NewSystemDisk.vhdx` 大小 | 11,972 MB | 11,972 MB | 11,972 MB |

CPU 时间一秒都不涨 = 进程不是在算，是在**等**。这不是「慢」，是真死锁。

#### 根因：v1.7 为了显示进度改的那段管道读取会自己锁死

v1.7 用 `Process.StandardOutput` 逐字符读，靠 `Peek()` 判断有没有数据：

```powershell
while ($true) {
    if ($reader.Peek() -lt 0) {
        if ($proc.HasExited) { break }
        Start-Sleep -Milliseconds 100
        continue
    }
    $ch = $reader.Read()
```

`Peek()` 在管道暂时没数据时**并不总是阻塞**，可能直接返回 -1。此时 DISM 还活着，
`HasExited` 是 false，脚本就掉进「睡 100ms → 继续」的无限空转，**再也不去读管道**。
DISM 的 stdout 缓冲（约 4KB）写满后彻底阻塞 —— 双方互等，界面也因为不再 `DoEvents` 而假死。

顺带解释了为什么 v1.6 反而没卡：那时是同步 `ReadLine()`，进度刷不出来（看着像卡），
但不会互等，最终还是能装完。v1.7 为了修「进度不动」反而把流程锁死了。

#### 修法：DISM 输出走文件，主线程轮询

- `Start-Process -RedirectStandardOutput` 到临时文件。**文件没有固定大小的缓冲区**，
  DISM 永远不会因为没人读而阻塞，这是从机制上消灭死锁。
- 主线程每 0.8 秒做三件事：读文件取最近的百分比、读目标盘已用空间、调用 `$report`
  刷新界面（`$report` 内部有 `DoEvents`，窗口不会假死）。
- 界面从此一直显示 **「正在恢复系统文件 42%　已写入 12.3 GB」**。
  哪怕 DISM 一个字都不打印，「已写入」的数字在涨就说明活着。
- 看门狗：连续 4 分钟既没输出、已用空间也不涨 → 结束 DISM，并给出人能看懂的原因
  （硬盘响应异常 / 杀毒软件实时扫描 / 镜像损坏）和下一步建议。
- 去掉 `/CheckIntegrity`：它让这一步慢 20~30%，而 wim 真坏了 Apply 一样失败，救不回来。
- `Start-Process -PassThru` 拿到的对象在进程退出后 `ExitCode` 常读成 `$null`，
  所以判断成功改成三选二：**退出码 / 内核文件在不在 / DISM 有没有打印成功字样**。

#### 同一份日志里还有第二个致命问题：虚拟磁盘里有 2 个分区

```
[11:59:33] [INFO] 虚拟磁盘分区数: 2 （native boot 要求 = 1）
[11:59:33] [WARN] 分区数不是 1，开机可能找不到系统
```

这行 WARN 是真的会致命：

`diskpart` 的 `clean` → `convert gpt` → `create partition primary` 会在 GPT 表里
**自动插入一个 16MB 的 MSR(Reserved) 分区**，于是变成

```
分区1 = Reserved(MSR)   ← 空的，没有文件系统
分区2 = 系统分区        ← 系统装在这里
```

而 bootmgr 用 `vhd=` 定位时取的是虚拟磁盘的**第一个分区**，也就是那个空 MSR →
重启后要么菜单里没条目，要么选了进不去。这正是 v1.4 反复强调「必须单分区」的原因，
只是当时用的是 diskpart，谁也没想到 `convert gpt` 会偷偷塞一个 MSR 进来。

修法（v1.8 起）：

- `clean` 仍交给 diskpart（这条路径已验证可用），**分区改用
  `Initialize-Disk -PartitionStyle GPT` + `New-Partition -UseMaximumSize` + `Format-Volume`**
  —— 这套命令只写 GPT 头和一个数据分区，不会建 MSR。
- 万一某些环境下还是冒出 Reserved 分区，当场 `Remove-Partition` 删掉再复核一次。
- 分区数 ≠ 1 从「写个 WARN 继续装」改成 **立刻失败并清理**。
  以前要等装完 20 多分钟、重启才发现白装，现在 10 秒内就知道。

#### 配套：新增「清理安装残留」工具

卡死或中途关掉窗口之后，机器上会留三样东西：还在跑的 `dism.exe`（占着 vhdx）、
挂着的虚拟磁盘（占着 E: 之类盘符）、半成品的 `NewSystemDisk.vhdx`。

双击 **`清理安装残留-管理员运行.bat`** 一次性清掉，它会依次：结束 dism → 卸载所有
`File Backed Virtual` 虚拟磁盘 → 找到所有 `NewSystemDisk.vhdx` 并逐个询问是否删除。
只动这个文件名，其它虚拟磁盘一律不碰。

### v2.1 新增：装完自动注入本机网卡驱动（实测可行）

#### 为什么要做这个

`maimai3_nohdd.wim` 这种 Dism++ 精简镜像把原主机的 OEM 驱动剔掉了。
装出来的新系统里，**网卡是「未知设备」** —— 有线 5GbE 和 Wi-Fi 6E 都不认，
开机第一件事就是没网，只能拿 U 盘拷驱动过去，很难受。

本机实测的网卡是这两块（都是 2020 年之后的芯片，Win10 19041 自带驱动认不了）：

| 类型 | 型号 | 硬件 ID |
|---|---|---|
| 有线 | Killer E5000B 5 Gigabit Ethernet | `PCI\VEN_10EC&DEV_5000` |
| 无线 | Realtek 8852CE WiFi 6E | `PCI\VEN_10EC&DEV_C852` |

#### 做法：把「本机正在用的驱动」搬过去

不下载通用驱动包，而是直接从当前系统导出网络类驱动，再 DISM 注入到新系统。
驱动就是从同一台机器上取的，**硬件 ID 必然匹配**，装完就有网。换一台机器装也适用。

流程（已集成到安装器，`& $report 88` 那一步）：

```
pnputil /enum-drivers         → 列出所有第三方驱动
  ↓ 按 Class GUID {4d36e972-e325-11ce-bfc1-08002be10318}（网络适配器）筛选
pnputil /export-driver oemNN.inf <临时目录>
  ↓
dism /Image:E:\ /Add-Driver /Driver:<临时目录> /Recurse
```

本机实测：166 个第三方驱动包里筛出 **9 个网络类包**，导出 5.3 MB。
其中 `oem130.inf` 就是 Killer 的 `e2k68cx21x64.inf` —— 正是有线网卡那个。

#### 踩到的三个坑

**① `Export-WindowsDriver` 根本没有 `-Class` 参数**

第一版写的是 `Export-WindowsDriver -Online -Destination $d -Class Net`，
实测直接报「找不到与参数名称 Class 匹配的参数」（Dism 模块只暴露 `Destination`、`Online`）。
不带筛选会把显卡、声卡、蓝牙全导出来，几百 MB 到几 GB。所以改用 pnputil 自己筛。

**② 筛选不能靠「类名」，要靠 Class GUID**

中文系统上 `pnputil /enum-drivers` 输出的是「类名: 网络适配器」，
英文系统是「Class Name: Net」，两边都匹配会很难看。
`{4d36e972-e325-11ce-bfc1-08002be10318}` 是 Windows 定义的固定 GUID，跟语言无关。

**③ `dism /Image:"E:\"` 的结尾反斜杠会吃掉引号**

`"/Image:E:\"` 传给命令行时，`\"` 被当成转义引号，参数会变成 `Image:E:"`。
盘符路径本来就没有空格，直接 `'/Image:{0}:\'` 不加引号最稳。

#### 失败不影响安装

驱动注入整段包在 try/catch 里，失败只写一条 WARN 继续往下走 ——
系统本身是完好的，只是可能没网，插 U 盘装驱动也能救，没必要把 20 分钟的安装作废。

另外新增独立工具 **`注入网卡驱动-管理员运行.bat`**，用于「已经装好了才发现没网」的场景：
自动认虚拟磁盘里的系统 → 导出本机网络驱动 → 注入 → 打印结果。

> 如果注入了还是没网，说明本机驱动要求的系统版本比镜像高（Win11 驱动装进 Win10 19041
> 就是这种情况）。那就去网卡官网下 Win10 版驱动，在目标系统里手动装一次。

#### v1.1 修复：注入工具往「正在运行的系统」里写（Error 87，有直接报错证据）

第一版把「带 `\Windows\System32\ntoskrnl.exe` 的卷」都当成目标。
问题是**正在运行的 C: 本身就带内核**，而虚拟磁盘没挂载时 C: 是唯一候选，
于是脚本选定了 C:，DISM 直接拒绝：

```
Error: 87
The /Image option that is specified points to a running Windows installation.
To service the running operating system, use the /Online option.
```

**DISM 是拒绝执行的，因此没有往 C: 写任何东西，原系统完好。**
但这个错误本身说明目标定位逻辑是错的 —— 换成别的命令（比如 `bcdedit`、`dism /Cleanup-Image`）
就可能真的改到原系统。

v1.1 起改成三条：

1. **排除运行中的系统**：先取 `$env:SystemDrive` 的卷 `UniqueId`，凡 UniqueId 相同或盘符相同的卷，
   一律标记 `Running=True`，不进候选池（同一卷被挂到第二个盘符也能识别）
2. **优先认虚拟磁盘**：`Get-Disk` 里 `BusType` 为 `File Backed Virtual` 的磁盘上的卷才是首选，
   并且显示成「虚拟磁盘里的系统」
3. **没挂载就自己挂**：扫描所有本地固定盘根目录下的 `NewSystemDisk.vhdx`，
   `diskpart attach vdisk` → 重新枚举 → 注入完 `detach vdisk` 还原

另外加了一道双保险：哪怕用户手选，只要 `Running=True` 就直接中止退出。
候选为空时明确写「当前运行的是 C:，它不能作为目标」，不再静默挑一个。

实测（非管理员环境下抽取脚本里的定位代码运行）：C: 被正确标记 `Running=True`，
可用目标 0 个，同时正确找到 `D:\NewSystemDisk.vhdx` 准备挂载。

#### v1.9.1 修复：分区数误报警告

删掉 MSR 后 GPT 不会重新编号，系统分区仍然是 2 号。旧代码拿「分区编号」和 1 比，
于是每次装完都会打一条 `系统分区不是 vhdx 的第一个分区，开机很可能找不到系统`。
改判「分区总数」后，正常安装不再出现这条误报。

## 装完设备管理器一堆未知设备（不是缺网卡，是缺整批驱动）

现象：进了新系统，网卡不认，而且设备管理器里从「其他设备」到「系统设备」一排感叹号。

原因有两层：

**① 只搬了网络类，剩下的根本没搬**

第一次注入只筛选了 Class GUID `{4d36e972-...}`，本机 164 个第三方驱动包里只有 9 个是网络类。
剩下的 106 个 `System` 类（芯片组、ACPI、PCIe、Thunderbolt）、4 个 `Display`、
2 个 `Bluetooth`、3 个 `MEDIA` 一个都没进去，所以那些设备当然还是未知设备。

**② 驱动进了 DriverStore ≠ 绑到了设备上**

`dism /Image:X\ /Add-Driver` 只是把驱动**放进**驱动库（staging）。
真正绑到设备是目标系统**下次开机时 PnP 自己匹配**的结果。
所以注入成功（日志里 8 个 `successfully installed`）不代表设备已经认出来了；
如果那批驱动本身不适用（比如 INF 里限定了 `NTamd64.10.0...22000` 以上），
staging 会成功，绑定时仍然认不出。

对应两个工具：

| 工具 | 在哪跑 | 干什么 |
|---|---|---|
| `全量注入驱动-管理员运行.bat` | 原系统（管理员） | 自动挂 vhdx → 导出本机全部 160+ 个驱动包 → 一次注入 → 按成功/未适用分类报告 → 卸载 vhdx |
| `新系统-诊断并装驱动.bat` | **新系统里** | 列出所有带感叹号的设备（含硬件 ID 和问题码）→ 用留存的驱动 `pnputil /add-driver /install` 现场装 → 报告写到各盘根目录的 `新系统诊断.txt` |

`全量注入驱动` 会顺手把导出的驱动另存到 **`<vhdx 所在的盘>:\NewSystemDriver`**，
所以进新系统后那个目录还在，诊断工具能直接拿它现场装 —— 不用再插 U 盘。

注入完成后看报告里的「未适用」清单：那批就是 Win11 驱动喂不进 Win10 的，
只能去主板/网卡官网下 Win10 版。`新系统诊断.txt` 里的硬件 ID 可以直接拿去对型号。

### 诊断报告里 500 多个「未知设备」其实是假的（CM_PROB_PHANTOM）

克隆镜像里带着**来源机器**的整份设备树。换到新硬件后，那些设备不在了，
注册表里的记录却留着，`Get-PnpDevice` 会把它们报成 `Status=Unknown / Problem=45`。
实测一份报告 558 条问题设备里，**553 条是 phantom**，真故障只有 5 个。

诊断工具 v1.1 起跳过 `Problem = 45`（phantom）和 `22`（被禁用），
只报真正装不上的，报告从 4000 多行降到几十行。

### 本机实测结论：Killer E5000B（5GbE）在 Win10 上没有可用驱动

| 设备 | 硬件 ID | Win10 19045 能不能装 |
|---|---|---|
| Killer E5000B 5GbE | `PCI\VEN_10EC&DEV_5000` | **不能**，见下 |
| Realtek 8852CE WiFi 6E | `PCI\VEN_10EC&DEV_C852` | 能，有官方 Win10 包 |

`e5xw11x64.inf`（Killer 官方）的 `[Manufacturer]` 写的是：

```ini
%Provider%=Killer, NTamd64.10.0...22000
```

`...22000` 意思是**最低 build 22000**（Win11 21H2）。Win10 19045 永远低于它，DISM 能
staging 成功，绑定时一定失败（设备显示代码 28）。
去 Microsoft Update Catalog 查 Killer 也只有 `1125.x / 1126.x`，全部标注
「Windows 11 Client, 22H2 and later」，没有 Win10 分支。RTL8126 是 2024 年的芯片，
Realtek 没为它出 Win10 驱动 —— 这是硬限制，注入救不回来。

所以这个系统里**走 WiFi**，或者插一个 Win10 自带驱动的 USB 网卡
（RTL8152/8153、或手机的 USB 网络共享，19045 都有内置驱动）。

### v1.0 现场安装为什么「一个包都没装」

报告里 `驱动目录: E:\NewSystemDriver （154 个 INF）`，紧接着
`pnputil 结果: 成功导入 0 个包 / 驱动程序包总数: 0`。
v1.0 用的是 `pnputil /add-driver <目录> /subdirs /install`，而 `export-driver`
导出的是**每个包一个子目录**，`/subdirs` 在这台机器的 pnputil 上没有生效，
于是顶层扫到 0 个 INF。

v1.1 改成：先取每个故障设备的硬件 ID，去 INF 文本里找匹配项，
再对匹配的 INF 逐个 `pnputil /add-driver "<inf>" /install`。
150 多个包只会跑真正相关的那几个，几秒完成。

## 任务管理器里多出一张「空 GPU」

现象：性能页里除了正常的显卡，还多一张完全没有数据、显存和 3D 使用率永远是空的 GPU。

### 先分清两件完全不同的事

| | 会不会占任务管理器的 GPU 位 | 成因 |
|---|---|---|
| **IDD 虚拟显示器** | **会**，这就是那张空卡 | 串流 / 模拟器 / 投屏软件装的「间接显示驱动」，设备实例是 `ROOT\DISPLAY\NNNN`，由软件自己造出来，没有真实 DX 引擎 |
| 幽灵记录 | **不会** | 克隆镜像带来的原机器显卡记录，设备已不在本机，只在「显示隐藏的设备」里能看到 |

任务管理器只枚举**正在活动的**适配器，幽灵设备根本不会被枚举。所以删幽灵对那张空卡**毫无作用**。

### v1.0 踩过的两个坑（已修，v2.0）

1. **找错了对象**：把空 GPU 当成幽灵卡，删了半天当然没变化。
2. **只信退出码**：`pnputil /remove-device` 对一个**完全不存在**的设备 ID 也返回退出码 0。v1.0 拿这个当「删除成功」，报告写「成功 3 个」而记录可能一条都没动。实测验证过这个行为，所以 v1.0 的清理结果完全不可信。
3. **删除顺序反了**：`Remove-PnpDevice`（走 `DIF_REMOVE`，能处理不在位设备）才是主力，`pnputil` 只是补充。v1.0 先试 pnputil 且判成功就跳过，等于永远不修。

### 用 v2.0

**`急救工具\新系统-清理幽灵显卡.bat`**（在虚拟系统里跑，管理员）：

1. 把每张适配器分成 **真实在用 / 虚拟显示器 / 幽灵 / 故障** 四类列出来
2. 直接告诉你那张空卡是哪一个虚拟显示器造出来的
3. 问你两件事，分开处理：
   - **禁用虚拟显示器**（消除空 GPU，推荐）—— 禁用后任务管理器不再显示，要用串流/模拟器时再启用回来
   - **清理幽灵记录**（只是让隐藏设备列表干净，不影响使用）
4. **删完重新枚举复核**，报告里明确写「已消失 / 仍在」，不再靠退出码猜

报告写到各盘根目录的 `显卡诊断.txt`。禁用后重启一次，GPU 列表才刷新。

### 虚拟显示器是从哪来的

「全量注入驱动」会把本机 160+ 个驱动包整体搬过去，其中就包括 GameViewer、MuMu 这类
软件装的 IDD 驱动。注入后新系统首启时 PnP 会照 Root 枚举 ID 建出设备，
于是多一张空 GPU。v1.1 的注入工具已经**自动排除**这类包（匹配 `GameViewerIdd`、
`IddDriver`、`usbmmidd`、`VirtualDisplay`、`MuMuIdd`、`spacedesk` 等，实测只命中这 2 个，
不会误伤 NVIDIA / Intel 真显卡），并在界面上列出排除了哪几个。

所以重装一次系统，不会再冒出这张空卡。已经装好的，用上面的 v2.0 工具禁用掉即可。

## v1.11：多系统 + 自定义名称 + 自定义路径（2026-11-04）

这一版解决的是三个"不是 bug 的设定问题"：

### 1. 以前只能装一个系统

**原因**：vhdx 文件名写死成 `NewSystemDisk.vhdx`，预检里 `Test-Path` 一命中就直接 `throw`
「已经装过一次了」，于是第二次装必然失败。

**现在**：文件名由用户输入的名字生成，重名自动加 `(2)`、`(3)`……

```powershell
# 旧
$vhdPath = Join-Path "$($DriveLetter):\" 'NewSystemDisk.vhdx'

# 新
$safeName = Get-SafeDiskName $DiskName            # 清洗非法字符
$vhdPath  = Get-UniqueVhdPath -Folder $dir -DiskName $safeName   # 名称 / 名称(2) / 名称(3)…
```

### 2. 名字要能自己起，而且要显示在开机菜单里

启动项 `description` 不再拼接「（新系统）」，直接用用户输入的名字：

```powershell
if ($DisplayName) { $desc = $DisplayName }
elseif ($EditionName) { $desc = "$EditionName（虚拟系统）" }
else { $desc = 'Windows（虚拟系统）' }
```

写完之后会 `bcdedit /enum` 读回来比对，**不一致就重写一次**（老版本遇到过中文描述读回变乱码），
实在不行就剥离非 ASCII 字符后重写，保证菜单里一定是你起的名字。

名称的清洗规则（`Get-SafeDiskName`）：

| 情况 | 处理 |
|---|---|
| `\ / : * ? " < > |` 和不可见控制字符 | 直接去掉 |
| 尾部 `.` 或空格 | 去掉（Windows 文件名规则） |
| 超长 | 截到 48 字符 |
| `CON` `PRN` `AUX` `NUL` `COM1-9` `LPT1-9` | 后面补 `-` |
| 空 | 回落成 `WinVHD` |
| emoji / GBK 编不出的字 | **明确拦截**并提示换名（否则 diskpart 会写出一堆 `?` 建不出文件） |

### 3. 存放位置要能自己选

第 ② 步从「只能选盘符的下拉框」换成：

- **可编辑路径框**：`D:\VHD`、`E:\系统\游戏` 都行
- **盘符快捷按钮条**：点一下填成 `X:\`
- **「浏览...」**：标准目录选择框，可以顺带新建文件夹

路径校验（`Test-TargetFolder`，全部在点「开始」前拦下，不会装到一半才失败）：

| 检查 | 不通过时的提示 |
|---|---|
| 空 / 相对路径 / 含 `..` | 要写完整路径，例如 D:\VHD |
| 目录不存在 / 是个文件 | 这个文件夹还不存在 |
| 盘不存在 | 找不到 X: 这个盘 |
| 非本地固定盘 | X: 不是本地硬盘（U 盘/网络盘/光驱都不行，开机时读不到） |
| 非 NTFS | X: 是 exFAT 分区，必须用 NTFS |
| 在 `Windows` / `Program Files` / `ProgramData` / `Users` 下 | 别放进这些系统目录 |
| GBK 编不出的字符 | 路径里有 GBK 编不了的字 |

另外路径框下面那行会实时显示「剩余 xx GB」，不够装时立刻变红。

### 4. 项目改名为「虚拟硬盘系统」

- 窗体标题、顶栏、日志文件名（`虚拟硬盘系统-YYYYMMDD.log`）、bat 窗口标题、
  `开始.bat` 菜单抬头全部替换
- 内部变量统一走 `$Script:ProductName`，以后改名只改一处

### 5. 卸载器跟着升级（v1.8）

- 不再只认固定文件名，改为扫各固定 NTFS 盘根目录 **和下一层子目录**的 `*.vhdx`
- 老名字 `NewSystemDisk.vhdx` / `新系统.vhdx` 依然收进来（老用户升级后照样能卸）
- 列表每条显示 **系统名称 + 占用空间 + 完整路径**（名称取自状态文件里的 `Desc=`)
- 确认框和完成提示都带上名字，装过多个时不会删错

## v1.12：修「明明有几百 GB 却报空间不足」（2026-11-04）

### 现象

用户在 `D:\虚拟磁盘` 安装，弹窗：

```
空间不够。
目录 D:\虚拟磁盘 所在分区剩余 0 KB，需要 45.0 GB。
```

但同一时刻实测这块盘：`Get-Volume` → 436.7 GB 可用，`Get-PSDrive` → 436.7 GB，
`[IO.DriveInfo]::new('D:\')` → 436.7 GB，`D:\虚拟磁盘` 目录也确实能正常写入。
**三处口径全都正常，程序却报 0 KB。**

### 根因

v1.11 里这段判断有两处毛病叠在一起：

```powershell
if (($lblDrive.Tag -eq 'bad') -or ($vol.SizeRemaining -lt ([int64]$size * 1GB + 5GB))) {
    $freeTxt = Format-Size $vol.SizeRemaining     # ← 打印出来的就是这个 0
```

1. **`$vol` 是上面某个分支遗留下来的旧对象**，不是当前目录的卷；
   而且 `Get-Volume` 的 `SizeRemaining` 在某些时机（卷刚被挂载/刷新、盘符与卷关联短暂不一致、
   目标目录位于动态扩展卷上）会返回 0。**单一数据源不可信。**
2. **判断里混进了 UI 状态**（`$lblDrive.Tag`）。这个 Tag 由文本框的实时校验写入，
   而校验会因「报告值 0」先被打成 `bad`，于是点「开始」时直接短路报错，
   根本没机会重新取一次数 —— 自己把自己锁死了。

### 修法

**1. 三路取数，取最大值**（`Get-DiskFreeBytes`）

```powershell
Get-Volume -DriveLetter D  →  SizeRemaining      （0，被丢弃）
[IO.DriveInfo]::new('D:\') →  AvailableFreeSpace （468 GB）
Get-PSDrive -Name D        →  Free               （468 GB）
                            → 取 max = 468 GB
```

任何一路拿到大于 0 的数就采信。只有「盘根本不存在」才返回 -1。

**2. 真写一个 64MB 的探针文件**（`Test-FolderWritable`）

报告值终究只是报告值 —— 配额、只读挂载、父目录拒绝写入 ACL、被安全软件挂钩的目录，
都可能「报告很漂亮但写不进去」；反过来「报告 0 但实际能写」这次也真的发生了。

所以点「开始」时做一次真实写入：在该目录建一个 64MB 临时文件（`SetLength` 稀疏写，
秒级完成），成功就删掉。结果只有两种：

| 探针结果 | 处理 |
|---|---|
| 写得进 | 继续装（即使报告值显示不够） |
| 写不进 | 报错，并在弹窗里分开写「系统报告剩余」和「实际写入测试：<具体原因>」 |

失败原因会被翻译成人话：无写入权限 / 磁盘已满 / 分区只读 / 其它原始异常。

**3. 判定顺序调整**

```
报告值 ≥ 需要  → 再做一次探针，通过才继续（防配额/ACL 类问题）
报告值 < 需要  → 先做探针，写得进就照装，写不进才报错
```

任何一步都不再看 `$lblDrive.Tag` —— UI 状态只影响那行提示文字的颜色，不参与放行决策。

### 验证

| 项目 | 结果 |
|---|---|
| 10 个 ps1 语法检查 | 全 OK |
| 结构断言（含新增 5 条） | 34/34 PASS |
| `Get-DiskFreeBytes` 取数（D 盘、C 盘、子目录、不存在的盘） | 5/5 PASS |
| `Test-FolderWritable`（普通目录、`D:\虚拟磁盘`、System32、不存在目录） | 4/4 PASS |
| 探针文件是否留残渣 | 两个目录均 0 残留 |
| 10 个 bat SHA256 与 ps1 一致 | 全一致 |

实测 `D:\虚拟磁盘` 的探针结果：**可写**，说明这个目录本身没有任何问题，
之前纯粹是被错误的空间数字挡住的。

用新版 `双击我-装系统.bat` 重新打开，同样填 `D:\虚拟磁盘`，界面上会显示

## v1.13 修复：装到子目录时，开机菜单指向错文件（2026-11-04，已实测根因）

### 现象

装到 `D:\虚拟磁盘\maimai.vhdx`，安装全部成功、菜单条目也建好了，
但开机菜单选中这一项进不去（`0xc000000f` / 找不到文件）。
另外「这台机器上已经装过的系统」列表和卸载器里都看不到这个系统。

### 根因（安装日志里有直接证据）

`%TEMP%\虚拟硬盘系统-20261104.log`：

```
[17:37:44] [INFO] device => vhd=[D:]\maimai.vhdx          ← 少了一层「虚拟磁盘\」
[17:37:44] [INFO] bcdedit set [... device vhd=[D:]\maimai.vhdx] => exit=0
```

构造设备路径时只取了文件名：

```powershell
$vhdFile = [System.IO.Path]::GetFileName($VhdFullPath)   # 只剩 maimai.vhdx
$dev = "vhd=[$($vhdDrive):]\$vhdFile"                    # 目录被丢了
```

`bcdedit` 返回 `exit=0`，启动条目确实建好了、`displayorder` 里也有它，
所以「看着一切正常」—— 但指向的文件不存在，一选就失败。

同一个错误的三个连带问题：

| 位置 | 症状 |
|---|---|
| 安装器写 `vhd=` | 菜单指向 `D:\maimai.vhdx`，文件实际在 `D:\虚拟磁盘\` |
| 安装器「已装系统」列表 | 用 `Get-ChildItem -LiteralPath "D:\*"` 扫子目录 —— **`-LiteralPath` 不展开通配符**，永远 0 结果 |
| 卸载器 | 只扫盘根目录，完全不看子目录，根本找不到这个系统 |

### 改法

**1. 路径转换统一走一个函数**（安装器、修复工具都用它）

```powershell
# D:\虚拟磁盘\maimai.vhdx -> vhd=[D:]\虚拟磁盘\maimai.vhdx
function Get-VhdBcdDevice {
    $full = [System.IO.Path]::GetFullPath($FullPath)
    $root = [System.IO.Path]::GetPathRoot($full)          # D:\
    $letter = $root.Substring(0, 1).ToUpper()
    $rel = $full.Substring($root.Length)                  # 虚拟磁盘\maimai.vhdx
    return "vhd=[$($letter):]\$rel"
}
```

**2. 写完当场逐字核对**（不再只看「有没有 `vhd=`」）

```powershell
$backFull = Get-FullPathFromBcdDevice $dm.Groups[1].Value   # 从 bcdedit 输出反解
if ($backFull -ne $wantFull) { 重写一次；还不对就直接报错，不假装成功 }
```

**3. 扫描子目录改用「广度优先 + 剪枝 + .NET 枚举」**

`Get-ChildItem -LiteralPath` 不能带通配符（这是这次的核心坑），
`-Path` 能带但在系统目录里遍历太慢。最终方案：

- 自己维护队列按层遍历，按**目录名**跳过 `Windows` / `Users` / `$RECYCLE.BIN` 等
- 跳过 reparse point（ junctions ），避免绕回自己
- 用 `[System.IO.Directory]::GetFiles/EnumerateDirectories` 而不是 `Get-ChildItem`
  （同一棵树实测 **83 ms vs 1074 ms**）
- 默认深度 6 层，够覆盖任何手选路径

**4. 卸载器**：同样扫描到子目录，精确匹配串改成带子目录的完整路径
（`vhd=[D:]\虚拟磁盘\maimai.vhdx`），不再依赖「同盘符 + 同文件名」的模糊兜底。

**5. 新增 `急救工具\修好菜单指向-管理员运行.bat`**

已经装坏的系统不用重装。它会：
- 找出所有带 `xxx.boot.txt` 的虚拟系统
- 逐字核对菜单条目指向的路径 vs 真实文件
- 不对就 `/set device` `/set osdevice` 改回来；条目丢了按记录补一条；没进显示顺序就 `addlast`
- 改完再读回验证；如果 `bcdedit` 处理不了路径里的中文，会明确告诉你换英文目录
- 动手前先 `bcdedit /export` 备份

### 验证

- 11 个 ps1 语法检查全部通过
- 结构断言 23/23 PASS
- 路径转换与扫描实测 14/14 PASS：子目录保留、盘符大写、多层目录、反向解析、往返一致、
  **能识别出 v1.12 写出的错误串**、能找到 `D:\虚拟磁盘\maimai.vhdx`、不含回收站、不含 Users
- 11 个 bat 与 ps1 SHA256 逐字节一致；`开始.bat` 11 项跳转无缺失

## v1.15（安装器 1.15 / 卸载器 1.10 / 修复启动菜单 1.5 / 清理安装残留 1.2）

这一版全部是「审查上一版时发现的新问题」，没有新功能。核心是两条 P1。

### P1-1 提示里的菜单序号指错了工具

安装失败时（系统文件已经写进虚拟磁盘、只有注册启动项那一步没成）会提示
「打开 `开始.bat` 选 7」。但 7 是「修好菜单指向」，8 才是「修复启动菜单」。

这不是简单的错别字 —— 那个时机 `.boot.txt` 还**没有**写（状态文件在启动项注册成功之后
才落盘），而「修好菜单指向」的前提恰好就是「有 `xxx.boot.txt` 的系统」。所以用户顺着提示
点进去，只会得到一句「没找到本工具装过的虚拟系统」，而真正能救他的第 8 项就在下面两行。

已改成「选 8（修复启动菜单）」。

> 两个工具的分工：**8 修复启动菜单** = 启动项压根没建出来，按 vhdx 补一条（不需要状态文件）；
> **7 修好菜单指向** = 启动项在、但指向错了（需要状态文件里的 GUID）。

### P1-2 修复工具会把「安装前的原值」改成「现值」

安装时记的是「装之前 BCD 里 `displaybootmenu` 是什么、有没有显式写过」。卸载时按它还原 ——
原本没设过的，用 `bcdedit /deletevalue` 抹掉，机器才回到「开机直接进原系统」。

但 v1.4 的修复工具在写状态文件时，是**对着当前 BCD 重新采样**的。而此刻 BCD 里已经是
安装器写进去的 `Yes` 了。于是只要中途跑过一次修复工具，状态文件就变成 `Yes / Set=1`，
卸载时按 `Yes` 还原，开机菜单**永远弹着**。

这正是 v1.8 / v1.9 花两个版本修掉的问题，从修复工具这里又绕了回来。

现在：只要状态文件已存在，`OrigTimeout / OrigDisplayMenu / OrigDisplayMenuSet / BcdBackup / Created`
一律沿用旧值，不再重新采样。只有首次修复（没有状态文件）才采样。

### P1-3 去重是「先删后建」，备份失败也照删

v1.4 为了「重复运行不叠加」，先按旧 GUID `/delete`，再 `/copy` 一条新的。
而上几行的备份逻辑是「备份失败只记一条 WARN，继续往下走」。

两件事凑一起：备份失败 + 旧条目已删 + `/copy` 失败 = 用户连原本能用的菜单都没了。
装好的系统因为跑了一次「修复」反而进不去，是最不能接受的一种坏。

现在顺序改成：**新条目建好 → 设备路径逐字校验通过 → 才删旧条目**。
最坏情况只是菜单里多一项，不再是「一项都不剩」。

### P2-4 清理安装残留会把别人的虚拟磁盘当成「半成品」

v1.1 全盘扫所有 `*.vhdx`，没有 `.boot.txt` 的一律归为「半成品 / 孤儿」，配的文案是
「20GB 就一直躺着」—— 这是在鼓励用户按 y。但 Hyper-V 的虚拟磁盘、别的装机工具建的 vhdx、
你自己放的备份，同样没有 `.boot.txt`。扫到 `D:\Hyper-V\...\xxx.vhdx` 就会请你删掉它。

v1.2 起分三类：

| 类别 | 判据 | 处理 |
|---|---|---|
| A 装好的系统 | BCD 里有它的启动项 | 一律不碰，只列出来看 |
| B 本工具装过、条目没了 | 旁边有 `.boot.txt` | 问 y，输入 y 就删（删完顺带清 `.boot.txt`） |
| C 不是本程序创建的 | 没有 `.boot.txt` | 列出来，但**必须照着输入文件名**才删；直接回车 = 跳过 |

C 类输错文件名会跳过，不会因为手滑就删掉。
（v1.16 起这句提示改得平和些：不再说「文件名不对」，改成告诉你「要删这一个请输入完整文件名 xxx」；
你输 `y` / `yes` 时会额外解释一句这一栏为什么不收 y。）

### P2-5 状态文件三个键名不统一

安装器写 `Name` + `Desc` + `Description` 三个；修复工具 v1.4 只写 `Description`；
安装器和卸载器读的是 `Desc`，读不到再退 `Name`。

结果：「用修复工具补过一次启动项」的系统，名字在那两个程序里都是空的，
自定义名字在这个边角上又丢一次。

现在统一按 **`Desc` → `Name` → `Description`** 依次退让，谁写的都能读出来；

## v1.16（安装器 1.15 / 卸载器 1.11 / 修复启动菜单 1.6 / 清理安装残留 1.3）

这一版只有一个目的：**修掉 v1.15 带进来的那个让「修复启动菜单」彻底不能用的回归**，外加两条顺手的收编。

### P0（回归）`/copy` 之后的 GUID 解析被整段删掉了

v1.15 改 P1-3（先建后删）时，把 `/copy` 后面「从输出里抠出新条目 GUID」的那几行一起删了，
只补回了 `$cp = Invoke-BcdEdit ...` 这一行。于是 `$guid` 在整个脚本里被引用十几次、**一次赋值都没有**。

后果是连锁的：

1. `/copy` 已经执行 —— BCD 里多了一条从 `{default}` 复制来的条目，描述写着新系统的名字（比如 maimai），设备却还指向原来的 C 盘；
2. 紧接着 4 条 `/set` 全部因为标识符为空而失败 → `$stepOk = false` → 抛「设置启动条目参数失败」；
3. 删旧条目的代码在校验之后，永远走不到。

也就是说：用户点「修复启动菜单」，看到的是失败，而菜单里那条叫 maimai 的选项点进去启动的是原系统。

> 关于「每跑一次就多一条」这一点，我核对后要更正一下：`catch` 里本来就有一步
> `bcdedit /import` 把 BCD 还原成修改前的备份，所以只要备份成功，那条半成品会被一起还原掉，
> **不会累积**；只有备份失败（或 import 也失败）时才会留下。不管哪种情况，现在都不会再有。

修法：

- 把那段恢复回来，并且比原来稳一点：优先匹配 `复制为` / `复制到` / `copied to` 后面的 GUID，
  语言或输出格式对不上时再退回「取输出里的第一个 GUID」，两种都拿不到就当场抛异常，
  绝不带着空 GUID 往下走。
- 额外加了**回滚**：`/set` 失败时先把刚建的那条 `/delete` 掉再抛；`catch` 里如果 BCD 没能整体还原，
  也会单独删掉这条。这样即使备份失败，也不会在菜单里留下一个点进去回原系统的坑。
- 那个「还原成功就不必再删」的状态记在 `$restored` 里，避免还原后才去删一个已经不存在的条目。

### 新增静态检查：变量被引用却没被赋值

这次的坑，语法检查（Parser 不报错）和结构断言（查的是「旧写法已清除 / 新函数存在」）都抓不到 ——
`$guid` 只有在 `bcdedit` 真的跑起来时才炸，而那一刻 BCD 已经被改了。

所以加了 `_源码\_build\lint_vars.ps1`，用 PowerShell 自己的 AST 做：

- 变量引用 = 所有 `VariableExpressionAst`；
- 变量声明 = 赋值左值 / `param(...)` 参数 / `foreach` 变量 / `$x++`；
- 声明**按作用域分开收**：脚本级一份，每个函数一份 —— 函数里读脚本变量是合法的，但
  A 函数的 `param($Guid)` 绝不能替 B 函数里的 `$guid` 作证（第一版就是这么漏的，

## v1.18：修复「第二台装到最后一步失败」（复制源失效）

### 现象（来自日志 20261104）

第一次装 Windows Server 2022 成功；紧接着装第二台（Windows 10 专业版）时，


`bcdedit /enum osloader` 当时只剩两个 `Windows Recovery Environment` 条目，

- `Minimum` 从 40 降到 **10**（工具本身的目标盘门槛就是剩余 10GB）。

## v1.31（2026-11-05 16:45）

**这一版没有新功能，只修了一处「会删系统文件」的隐患 —— 如果你之前跑过安装器或修复启动菜单，请务必更新。**

### 装完系统后清理垃圾目录，以前会把 `C:\Boot` 一起删掉

v1.28 及以前，安装器和「修复启动菜单」收尾时有一段「清理历史垃圾目录」：

```powershell
foreach ($junk in @('C:\EFI', 'C:\Boot')) {
    ...
    if ($age.TotalHours -ge 48) { continue }   # 只判这么一条
    Remove-Item -LiteralPath $junk -Recurse -Force
}
```

`C:\EFI` 确实是垃圾（UEFI 只读 ESP 上的 `\EFI`，C 盘这个没人用）。但 **`C:\Boot` 不是垃圾**，它是 Windows 的系统引导目录，里面有：

| 文件 | 作用 |
|---|---|
| `BCD` | BIOS/MBR 引导的启动配置数据库 |
| `BCD.LOG` / `.LOG1` / `.LOG2` | 活动 BCD 的事务日志 |
| `bootvhd.dll` | VHD 原生启动需要的组件 |
| `BOOTSTAT.DAT` | 启动耗时统计 |

而它的放行条件只有「创建时间 < 48 小时」一条。Windows 更新、装系统、修复引导都会重建这个目录 —— 也就是说，**只要机器在 48 小时内重建过 `C:\Boot`，下一次跑安装器就会把整个目录递归删掉**。

实测本机：`C:\Boot` 创建于 2026-11-03 19:24，检测那一刻的年龄是 **45.1 小时**，正好落在会被删的窗口里。

现在改成：

- `C:\Boot` **从清理列表里彻底移除**，代码注释里写死了「不要再加回来」
- `C:\EFI` 仍可清，但加了三道判断：48 小时内创建、子目录只有 `Microsoft`/`Boot`、**里面没有 `BCD` 或 `bootmgfw.efi`**（有就说明是活的引导目录，跳过）

### 清理安装残留：从「通配扫描」改成「白名单」

原来第 4 步用 `-Filter '*.bcd.LOG*'` 扫 6 个盘的根 + 一级子目录，再一把删除。

实测它确实没删到过系统文件 —— 但这靠的是 `-Filter` 的 8.3 短名匹配怪癖碰巧不匹配 `BCD.LOG`，**不是代码里有防护**。而 `C:\Boot\BCD.LOG` 跟我们要删的 `bcd-backup-xxx.bcd.LOG` 只差两个字母，换个写法或换台机器就可能命中。

现在改成白名单正则：

```
^bcd-[a-z]+(?:-[a-z]+)*-\d{8}-\d{6}\.bcd\.LOG[0-9]?$
```

必须同时满足「`bcd-` 开头 + 单词段 + 8 位日期 + 6 位时间 + `.bcd` + `.LOG/.LOG1/.LOG2`」才会被选中，覆盖历代三种命名：

- `bcd-backup-20261103-194815.bcd.LOG`
- `bcd-backup-fix-20261105-155106.bcd.LOG2`
- `bcd-rescue-20261105-120713.bcd.LOG1`

目录层面再排一遍 `Boot` / `Recovery` / `EFI` / `PerfLogs` / `Windows` / `Program Files*` / `Users` / `$Recycle.Bin` / `System Volume Information`，双保险。

实测（本机 49 个历史垃圾）：

| 文件名 | 会被选中 |
|---|---|
| `BCD.LOG` / `BCD.LOG1` / `BCD.LOG2` / `BCD` | 否 |
| `SYSTEM.LOG` / `SOFTWARE.LOG` / `bootmgr` | 否 |
| `bcd-backup-*.bcd.LOG*`（46 个） | 是 |
| `bcd-rescue-*.bcd.LOG*`（3 个） | 是 |

### 现在还有哪些地方会删东西

| 工具 | 删什么 | 怎么判定 |
|---|---|---|
| 装系统 | `C:\EFI` | 48h 内 + 只有 Microsoft/Boot + 无 BCD，任一不满足就跳过 |
| 装系统 | 无启动项的 vhdx | 只删本程序建的（有 `.boot.txt` 且条目已消失），逐个确认 |
| 卸载新系统 | 指定 vhdx + 它自己的条目 | 按记录里的 GUID / 路径精确匹配，不碰别的系统 |
| 修复启动菜单 | `C:\EFI` | 同上 |
| 清理安装残留 | 无启动项的 vhdx | A 类（有条目）一律不碰；C 类要输完整文件名 |
| 清理安装残留 | `bcd-*.bcd.LOG*` | 白名单正则，逐个列出后输 `y` 才删 |

**所有删除都要人工确认，没有一处是静默批量删。**

## v1.29（2026-11-05 16:20）：附属文件收进「虚拟硬盘系统-日志」，不再往盘根丢垃圾

### 为什么改

装完系统一看 D 盘根：27 个 `bcd-backup-20261105-150419.bcd.LOG` 这种文件。
`D:\虚拟磁盘\` 里还有 12 个。都是同一个来源 —— **`bcdedit /export` 导出的是一个

以前备份文件本身就写在 vhdx 旁边，于是：装一次系统 = 4 个文件（1 个 .bcd + 3 个 .LOG），
装在盘根就全糊在根目录上。安装日志还一直躺在 `%TEMP%`，装到哪都看不到。

### 改了什么

| 对象 | 以前 | 现在 |
|---|---|---|
| 安装日志 | `%TEMP%\虚拟硬盘系统-YYYYMMDD.log` | `<vhdx 目录>\虚拟硬盘系统-日志\虚拟硬盘系统-YYYYMMDD.log` |
| BCD 备份 | `<vhdx 目录>\bcd-backup-*.bcd` + 3 个伴生 LOG | 只留 `.bcd`，进 `虚拟硬盘系统-日志\` |

| 修复启动菜单（独立急救工具） | 备份硬写 `D:\bcd-backup-fix-*.bcd`、报告放工具目录 | 进第一个 vhdx 旁边的日志目录 |

**日志目录规则**：`<vhdx 所在目录>\虚拟硬盘系统-日志\`。
vhdx 在 `D:\虚拟磁盘\` → 日志在 `D:\虚拟磁盘\虚拟硬盘系统-日志\`；
vhdx 在 `D:\` 根 → 日志在 `D:\虚拟硬盘系统-日志\`。一条规则覆盖两种情况。

1. **BCD 备份改成「先导到临时目录，再拷 .bcd 到目的地」**

   闭包里每次运行先读数据槽，取不到才退回捕获值。这样切换日志目录后，
   按钮里报错、未处理异常写进日志的仍然是新位置。

装了两个 VHDX 系统，用 `开始.bat` 第 2 项卸载其中一个，重启后开机菜单只剩 Win11 一项。
菜单**是显示的**（`displaybootmenu=Yes`），所以不是菜单被关掉，而是**启动项真的从 BCD 里消失了**。

### 取证

- 修复前 `bcdedit /enum osloader` 只剩 3 条：Win11、Win11 的 WinRE、
  **Server 2022 的 WinRE（孤儿，指向已删的 vhdx）**
- 那个孤儿条目的 device 长这样：

  ```
  ramdisk=[[D:]\Windows Server 2022 Standard (Desktop Experience.vhdx,locate=custom:12000002]...
  ```

  —— **右括号 `)` 丢了，路径被截断**
- 四份 BCD 备份（`bcd-backup-20261105-150419 / 152027 / 152846`）对照：
  15:28 那份里 Win10 专业版的条目还在，之后整条消失

### 根因

镜像版本名叫 `Windows Server 2022 Standard (Desktop Experience)`，安装器直接把它当成了
vhdx 文件名。而 BCD 的 `vhd=[...]` 语法里 **`(` `)` 是定界符**，bcdedit 写进去、读回来
就被改写/截断。

后果是一串的：那个条目看着在、实际无效；进那个系统时 Windows 注册 WinRE 也按同一套
语法拼 ramdisk 路径，拼出来是坏的，**BCD 被写坏之后连带把别的启动项搞丢**
（Win10 专业版就是这么没的）。

### 修改

| 工具 | 版本 | 改动 |
|---|---|---|
| 安装器 | 1.26 → 1.27 | `Get-SafeDiskName` 把 `( ) [ ] { }` 一律换成 `-`；重名后缀 `名称(2)` → `名称-2` |
| 卸载器 | 1.12 → 1.13 | 卸完还剩 ≥2 个真实系统时**强制保留菜单显示**（以前无条件还原成「安装前的关/超时0」，多系统机器会把剩下那个藏起来） |

### 应急工具

`修复启动菜单-双击运行.bat`（自提权，先 `/export` 备份 BCD）：
按各盘 `*.boot.txt` 的记录重建丢失条目、补回 displayorder，并输出
`修复启动菜单报告.txt`（含修复前后完整 `bcdedit` 和历史 BCD 备份对照）。

> 这个救急脚本是直接调用同目录 `修复启动菜单.ps1` 的，**不在发行包的 zip 里**
> （发行包只放自解压 bat）。正式功能请用急救工具里的「修复启动菜单」。

## v1.25（2026-11-05 13:00）：修正镜像元数据被重复拼接（多版本镜像的版本表会错乱）

### 现象

多版本镜像（例如 Server 2022 的四个版本）在「版本」下拉里出现重复项、索引号乱跳；
单版本镜像看起来一切正常，所以这个问题长期没被发现。

### 根因

`Read-WimXml` 从文件尾部捞 XML 时，是在 UTF-16 字节流里找 `<W`（`<\0W\0`）。
XML 里每个 `<WINDOWS>` 标签都满足这个条件，而代码写完一段后**没有 break**，
用的是 `$xml += ...` —— 于是同一份 XML 被反复追加。

实测（一台真实单索引镜像）：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| `</WIM>` 出现次数 | 3 | 1 |
| XML 长度 | 2551 字 | 1113 字 |
| `<IMAGE` 数量 | 1（碰巧对） | 1 |
| 四索引假镜像解析出的版本 | 16 条（重复） | 4 条（正确） |

单索引镜像靠「正则只取第一个 DISPLAYNAME」侥幸正确，所以一直没暴露；
多索引镜像的 `<IMAGE>` 计数和版本表会成倍重复 —— 版本下拉里一堆重复项。

### 修法

找到第一处可截断的 XML 后**立即 break**，并改用赋值而不是追加。

### 顺带修的测试问题

这条测试（`edtest.ps1`，版本索引解析）**从来没被接进主检查**，而且它自己是红的：
`-Images @( @(..) @(..) )` 内层数组之间**漏了逗号**，脚本引擎把嵌套数组展平，
`$im[3]` 取到的是字符串的第 4 个字符（`'Windows...'[3]` = `d`，正是当时 XML 里
那个 `<TOTALBYTES>d</TOTALBYTES>`）。修好数据后 24 项全过，并已纳入 `run_check`。

## v1.24（2026-11-05 12:50）：走 /create 兜底建出来的启动项不进开机菜单

### 现象

BCD 主加载项被清空时（正是修复工具要救的场景），修复工具报「创建成功」，
但重启后开机菜单里**看不到新建的 WinVHD 这一项**。

### 根因

`bcdedit /copy` 会自动把副本加入 `{bootmgr}` 的 `displayorder`（开机菜单），
而 `bcdedit /create` **不会**。安装器和修复工具都只做了 create + set，没补 displayorder ——
条目本身是完整的（device/osdevice/path 都对），只是菜单里没有它。
全项目此前只有「修好菜单指向」这一个工具写了 displayorder。

### 修法

在共享函数 `New-BootEntryGuid` 的收尾统一处理（`/copy` 和 `/create` 两条路都走这里）：
先读 `{bootmgr}` 的 `displayorder` 行，已有该 GUID 就不动（避免打乱用户原有顺序），
没有才 `/displayorder {新GUID} /addlast`。安装器 → 1.24，修复启动菜单 → 1.10。

### 另外修掉的维护性问题

- **共享代码同步器不幂等**：`sync_common.py` 的「裸函数替换」分支只替换

  **每跑一次同步就多插一份注释**（实测 `Get-CopySourceGuid` 攒到 3 份）。
  现在会连注释块一起替换，并比较新旧文本；连跑三次全部 `[same]`。
- 新增断言：共享注释不重复、函数定义唯一、displayorder 三步齐全。

## v1.23（2026-11-05 12:20）：修正内置网卡驱动包目录名匹配（v1.22 其实没生效）

## v1.22（2026-11-04 23:50 之后）：网卡注入补导出内置（in-box）驱动包

### 现象

用户反馈「注入驱动功能好像没有效果，前几个版本还有用的」。安装日志显示注入
本身每次都成功（DISM 退出正常、`vmxnet3.inf` 成功安装），但只导出了 1 个

之前「有用」是因为都在虚拟机里装：宿主机的 vmxnet3 恰好就是虚拟机要用的

1. `pnputil /enum-drivers` **只列第三方 oem\*.inf**——物理网卡常用系统内置

## v1.21（2026-11-04 21:10 之后）：单分区机进新系统后自动挂载原系统盘

### 现象

单分区机器（原系统 C: = 系统+引导+数据三合一，vhdx 也放 C:）装完进新系统，
原来的 C: 整个不见了——文件管理器里没有它，磁盘管理里它有分区但没盘符。

### 根因

不是工具弄丢了分区。进 VHD 系统后，原 C: 的角色从「启动卷」变成了
「系统分区」（bootmgr 在它上面），而 Windows 的规矩是：**系统分区和启动卷
不是同一个时，系统分区默认不分配盘符**（和 System Reserved 同款待遇）。
所以分区还在、数据都在，只是没有盘符。

### 修法

安装时往新系统里预埋微软官方首启钩子，首次进新系统后自动补盘符：

- `X:\Windows\Setup\Scripts\SetupComplete.cmd`：SYSTEM 身份、安装完成阶段
  自动跑一次（不需要用户登录，不弹窗）
- 同目录 `mount-host.ps1`：按安装时记录的「磁盘 UniqueId/签名 + 分区偏移」
  精确定位宿主分区，没盘符就分 **D: 起的第一个空位**（GPT 用 UniqueId 精确
  匹配，MBR 退回磁盘签名且签名为 0 时直接放弃防止误匹配；只认 GPT 基本数据
  分区和 MBR NTFS，ESP 之类一律跳过）
- 运行日志：`%WINDIR%\Temp\mount-host.log`，任何失败只记日志、不阻塞开机

已装好的旧系统想补盘符：进新系统用「磁盘管理」手动分配，或管理员 PowerShell
`Set-Partition -NewDriveLetter D`，一次永久生效。
